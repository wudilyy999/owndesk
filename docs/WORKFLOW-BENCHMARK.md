# CUA 流程对照与全成本记录

本工具用于设计1.25的C4/T22。复用原Task、DBOS、模型attempt、动作回执、人工请求和宿主检查，不启动第二套Agent。当前先覆盖Thunar创建父目录、创建子目录并重命名这一任务族。

## 1. 怎样理解这份对照

例如：第一次让Agent创建一个目录花了若干模型请求；随后又花请求提炼流程、验证和修订。后面一次流程执行即使没有模型请求，前面的开销仍然保留。

报告分开显示：请求次数、token、API费用、任务墙钟、模型请求时间、人工请求等待时间和成果检查。人工请求等了5分钟，并不能证明用户实际操作了5分钟；主动人工劳动当前显示未测量。缺失定价、未知回执和未完成样本各自保留。

## 2. 三个实验组与相同条件

| 组       | 执行方式                   | 约束                                      |
| -------- | -------------------------- | ----------------------------------------- |
| baseline | 原普通模型循环逐步操作     | 固定模型、GUI工具、相同完成合同           |
| checked  | 显式运行ready流程          | 每步新观察/窗口检查、最终宿主检查，零模型 |
| repair   | 同一流程，允许一次局部修订 | 修订使用冻结的同一模型和原账本            |

三个组各自使用一个独立工作站。每组执行相同的10组参数，各组之间不共享home，因此相同目录路径不会碰撞。固定实际验证镜像/协议/locale、坐标格式、模型配置、指令、记忆和参数。模型组受理前还会比较冻结的provider端点，禁止把更换后的本地固定响应当成原云模型。

`workstationChannel: "desktop"`在任务受理时冻结。模型只得到截图、键鼠、固定Thunar启动、人工问题/接管及完成工具；原runTool和executeAction还会检查通道，直接调用Shell也无法绕过。普通任务省略这个字段时保留原工具集合。

无检查参数复放的消融尚未提供，报告列为缺项；当前命令不会关闭已有控制/未知效果/宿主检查。真实模型质量、更多任务族和整体上游项目对照分别验收。

## 3. 冻结协议

先在一个专用实验安装中准备：

1. 一个经过3组独立检查的ready流程。
2. 三个使用相同名称、角色、模型、指令和初始记忆的Agent/工作站。
3. 10个不同父目录，参数名与流程声明完全一致。

规范文件示例：

```json
{
  "ownerId": "本安装拥有者ID",
  "versionId": "ready流程版本ID",
  "agentIds": {
    "baseline": "工作站A的Agent ID",
    "checked": "工作站B的Agent ID",
    "repair": "工作站C的Agent ID"
  },
  "cases": [
    {
      "id": "sample-1",
      "parameters": {
        "parentName": "Benchmark-parent-01",
        "draftName": "Draft 01",
        "readyName": "Ready 01"
      }
    }
  ]
}
```

`cases`实际必须恰好10项，上面仅展示一项的格式。

```sh
npm run workflow:benchmark -- freeze /绝对路径/spec.json /绝对路径/实验目录
```

创建私有`manifest.json`，禁止覆盖同名文件，不受理任务、不请求模型。此后配置发生变化时提交会明确拒绝。早期缺少provider端点的协议只允许继续确定性组；模型组必须重新冻结新协议。

## 4. 逐项提交与观察

```sh
npm run workflow:benchmark -- submit /绝对路径/manifest.json checked sample-1
```

这个命令只经原submitTask受理/入队。原worker负责执行，命令不替代worker，也不替代人工确认。重复相同组/样例返回同一个Task；已知回执恢复和未知效果复核继续遵守原规则。

`baseline`和`repair`组可能产生API费用。必须先解决已有未知请求的重试授权，保持费用记录，再按明确授权执行真实模型验收。出现模型响应丢失或外部效果未知时，停止检查原Task，不新建替代样本来绕过。

观察每个Task的完成检查、原始事件和状态。目录检查在宿主只读提取后执行。当前Thunar英文适配支持带空格和中文文件名；镜像缺少部分中文字体，字节检查正确与截图字形完整是两个独立结论。

## 5. 收集历史成本

成本引用文件使用本工程保留的原始数据库/Task身份，例如：

```json
[
  {
    "database": "原始实验数据库名",
    "taskId": "实际Task ID",
    "phase": "exploration"
  }
]
```

支持`exploration`、`compilation`、`validation`、`execution`、`repair`、`control`、`ui`。选择所有相关成功和失败；无新Task的合成事务检查不当成新的执行。读取使用只读事务，保留原请求时价格、已知费用、独立人工费用核对值和未知状态，不按今天的价格回写历史。

```sh
npm run workflow:benchmark -- collect /绝对路径/setup-refs.json /绝对路径/setup-metrics.json
```

数据库克隆保留同一Task和模型attempt身份：按Task ID与segment/decision/attempt去重。相同Task的不同副本数据冲突时明确失败，由操作者选择权威原始库，不静默挑选便宜副本。读取时省略截图、动作input、模型回答和凭据字段，仍保留完成合同、参数、文件名等元数据；协议还包含冻结的指令/记忆，必须按私有本地资料保管。

## 6. 报告与第一次交付的去重

```sh
npm run workflow:benchmark -- report /绝对路径/manifest.json /绝对路径/setup-metrics.json /绝对路径/report.json 首个已交付探索TaskID
```

首个探索Task必须已经完成且通过宿主检查。计量示例：

```text
普通策略：首个已交付探索 + 后续10个普通执行
流程策略：首个已交付探索 + 其他探索/编译/验证/修订开销 + 后续10个流程执行
```

这是11个实际用户交付位置的比较；首个探索在每个策略中各计一次。后续10组依旧是另行预冻结的新样本，历史探索不会被冒充为预冻结样本。若省略首个TaskID，历史探索全部作为设置开销，不声称它已包含在后续10次交付中。

失败/取消样本保留在计划分母10中。某组缺少样本、未结束、模型/环境/合同/通道不匹配时，不计算净收益；匹配组未全部完成固定检查时，也不把API费用差写成节省。费用有未知值时保留已知小计和未知数量，总额与金额回本保持空值。

报告同时列出中位数、范围、完成样本数量和原始Task引用。专属环境准备、参数提炼劳动、主动人工时间、基础设施费用和无检查复放消融仍有缺项，所以当前`fullC4Accepted`保持false。API小计与模型调用减少不能替代完整成本收益或产品优越性结论。
