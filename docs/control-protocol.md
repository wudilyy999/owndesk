# 工作站控制与恢复：实现协议

日期：2026-10-25。关联 P2—P4、G03/G04。这里记录已经进入代码的选择、实测范围和剩余缺口。
完整任务模型继续见 `docs/design/详细设计.md`；本文件对具体控制协议作实现级补充。

## 1. 用户能观察到什么

以“登录网站并下载报表”为例：

1. Agent 拥有一个独立 Linux 桌面。有界面 Chromium 由一个控制服务创建，DOM 操作、截图、人工操作共用这个浏览器。
2. 点击“连接桌面”得到观看连接。即使改掉前端的只读开关，观看服务仍丢弃输入。
3. 点击“接管桌面”先显示准备状态。worker 撤销旧连接、停止在途动作、清理按键后，才发出 `human_ready`。
4. 用户取得新控制连接，登录或操作。等待期间，工作站队列仍由当前任务持有。
5. 点击“交还给 Agent”，先关闭旧人工连接，再释放按住的按键和鼠标，改变控制版本。
6. 之后的模型必须重新观察。旧截图产生的决定和旧 DOM 引用不能直接继续执行。
7. 点击“取消任务”显示“正在停止实际操作”。确认工作站停止后，才把业务状态改为 `cancelled`。

自然语言模型循环已接通，受控 provider 经生产 SDK 驱动同一浏览器、人工登录与成果交付，人工等待期间重启 worker 也已通过。真实模型判断与完整个人 Agent 验收继续推进，详细协议见 docs/design/模型执行与成果验证.md。

## 2. 三个不同的标识

| 标识         | 谁生成                              | 解决的问题                 | 例子                                   |
| ------------ | ----------------------------------- | -------------------------- | -------------------------------------- |
| `epoch`      | 受信任 worker                       | 控制权变化后废弃旧命令     | 人工接管前为 8，交还后为 12            |
| `bootId`     | 每次控制器启动生成                  | 判断动作是否跨越控制器重启 | 原进程结束后，未完成动作的效果需要核对 |
| `dispatchId` | worker 根据任务/执行段/动作序号生成 | 相同逻辑动作只派发一次     | `任务ID-s1-a3`                         |

“控制权变了”和“进程重启了”分别记录。一个终端回执可能来自旧 boot，仍可作为恢复线索；新动作必须匹配当前 epoch 和 boot。

## 3. 实际进程与信任边界

```text
浏览器用户
  │ 拥有者会话 + 一次性票据
  ▼
Web / PostgreSQL                 worker（独占数据库租约）
  │ 仅写入请求                      │ Docker 生命周期、控制网关
  │                                 ├── 工作站容器
  │                                 │    Chromium + DOM 控制器 + Shell
  │                                 │    可修改自己的系统层与 home
  │                                 │    控制 VNC 5901（Docker exec stdin/stdout）
  │                                 │
  │                                 └── 独立观看容器
  │                                      只读系统层 / 无 home / 无 Docker socket
  │                                      只挂载 X11 socket
  └───────────────────────────────────── x11vnc 全局 -viewonly -noremote
```

工作站允许 Shell 和 sudo。因此把只读服务放进同一个可修改容器，无法建立可靠的服务器只读边界。
当前观看服务采用独立 sidecar：只读根文件系统、移除 capabilities、`no-new-privileges`，不挂载 Agent home、应用密钥或 Docker socket。

观看侧使用 `-noshm`。两个容器的 IPC 命名空间不同，通过 X11 socket 读取画面时不能沿用本机共享内存截图路径。
首次 UI 检查只确认连接成功，截图显示黑屏；补充实际画面像素检查后暴露此问题。修正后桌面与手机截图均有可见桌面。

边界说明：两容器共享同一 X server，观看连接读取的内容仍由 Agent 工作现场产生。任务成果的业务正确性继续由工作站外的验证器核对。
控制器回执与桌面显示都不构成防恶意代码的可信执行证明。Docker 也承担共享内核的容器边界，首版定位为单拥有者自托管环境。

## 4. 状态与迁移

| 当前状态    | 允许的操作                           | 下一步                                   |
| ----------- | ------------------------------------ | ---------------------------------------- |
| idle        | 为排队任务准备工作站                 | 取得任务后先进入 quiescing，再进入 agent |
| agent       | 匹配 epoch 的 Agent 工具、只读观看   | 接管、取消或释放                         |
| quiescing   | 撤销连接、停止输入；不开放新人工输入 | 确认后进入 human / agent / idle          |
| human       | 拥有者控制、只读观看；Agent 暂停     | 交还或取消                               |
| quarantined | 展示失败原因、允许用户取消           | 先确认容器边界停止，再由后续恢复流程处理 |

`desired_mode` 是持久化请求。API 写入请求后，不直接操作 Docker。worker 每 250ms 扫描，按工作站启动独立控制作业。
同一工作站生命周期操作使用同一串行锁；不同工作站不会互相等待一个缓慢的接管。
这是单 worker 内的互斥机制；数据库租约阻止第二个 worker 同时运行。扩展多 worker 前需要重新设计生命周期的跨进程所有权。

### 4.1 接管的分步事务

1. API 按“任务 → 工作站”的顺序锁行，确认拥有者与任务仍有效。
2. 创建或复用 `task_requests`，写入 `desired_mode=human` 与事件，同事务提交。
3. worker 把模式改成 quiescing，增加 epoch，撤销网关内的新旧连接。
4. 要求控制器停止新输入，等待在途浏览器操作结束，清理实际人工连接和按键。
5. 如果用过 Shell，采用第 5 节的冷边界策略。
6. worker 设置 human，再事务记录任务 `waiting_user` 与 `human_ready`。
7. 此时控制票据才允许签发。前端根据服务端确认状态获取新的控制连接。

如果第 4 步失败，worker 从宿主机停止并移除工作站，再登记 quarantined 与 needs_review。
如果 Docker 停止也失败，错误继续传播并触发安装级紧急停止，日志明确要求运维介入。

### 4.2 交还的分步事务

1. 用户提交请求 ID、payload 版本和 handback 决定；重复相同决定幂等，不同决定冲突。
2. worker 先撤销人工 WebSocket，等待上游连接关闭。
3. 检查工作站 5901 没有残存人工 TCP 连接，通过 X11 释放按住的键和鼠标按钮。
4. 增加 epoch，设置 agent；同事务解决请求并发送 DBOS 持久化消息。
5. 前端重新申请观看连接。模型运行时后续需要消费交还消息并重新观察。

关闭放大窗口仅隐藏界面，Agent 保持暂停。这样用户关掉页面时不会意外把仍未处理完的桌面交还。

## 5. Shell 与真实取消

仅杀进程组可以处理普通子进程。`setsid`、守护程序或重新建立的会话可能逃离该进程组。
因此取消采用宿主机 Docker 边界：

1. 先撤销观看/控制连接，任务取消标志已持久化，新的工具调用会检查它。
2. 停止观看容器与工作站容器；确认实际进程边界停止；移除工作站可写系统层。
3. 保留 home volume，便于保留报表、下载、浏览器 profile 和排查痕迹。
4. 停止受信任宿主机活动后，提交业务 cancelled 和 `cancel_workflow_pending=true`。
5. 后台取消 DBOS 工作流，再清除 outbox 标志；进程中断时可以继续完成这一步。

取消不依赖 guest 控制器回复。已实测控制器被 SIGSTOP 后，取消仍会停止并移除容器。

**接管/交还的代价**：同一 boot 使用过 Shell 时，采用冷边界清理；从镜像重建系统层，home 和 profile 保留。
Shell 安装进系统目录的软件、内存态网页和未落盘信息不会随重建保留。仅使用 DOM/桌面工具的正常交接保持热现场。
worker 重启时，优先依据 PostgreSQL 中的 Shell 历史判断冷恢复，在运行旧可写系统层前将其移除。

正常停止 worker 也停止本安装的工作站。worker 被强制结束后的时间窗口由下一次启动的 fencing 和动作核对处理；该行为没有被表述为瞬间停止。
数据库租约或控制循环异常时，worker 会尝试停止带本安装标签的全部工作站，避免失去控制后继续操作。

## 6. 动作意图与回执

### 6.1 正常调用

1. 校验任务、取消状态、工作站所有权和当前控制版本。
2. 同事务保存逻辑动作、实际派发尝试和 `tool_started` 事件。
3. 用稳定 dispatchId 查询 guest 回执，再决定是否派发。
4. guest 在执行外部效果之前先保存 running journal；执行后保存终端结果。
5. worker 取得结果后事务保存业务回执和事件。
6. guest 终端记录落盘后释放内存引用，避免所有历史截图一直积累在进程内。

执行意图记录并不等于动作已经成功。`status='intent'` 的动作要先核对，不能直接换 ID 重发。

### 6.2 两个已经验证的恢复窗口

**下载成功，worker 回执尚未提交：**

- 测试通过外部任务行锁阻止第 5 步提交，等待实际下载成功，然后 SIGKILL worker。
- 重启从 guest 终端回执恢复，同一下载请求计数仍为 1，派发尝试仍为 1。
- 如果只有文件而没有可用终端回执，可根据稳定目录核对下载完成；CSV 的业务内容仍需要另一个验证步骤。

**网站提交成功，响应尚未收到：**

- 测试站点记录 POST 后故意不回复，再结束 worker 和工作站控制器。
- 恢复发现该动作没有终端回执，状态进入 unknown / needs_review。
- 保留一条复核请求；提交次数仍为 1。系统不会以“没有响应”为理由自动重发。

### 6.3 分类与上限

| 动作                     | 中断处理                     | 证明范围                             |
| ------------------------ | ---------------------------- | ------------------------------------ |
| 截图、目录读取、DOM 观察 | 允许新的只读尝试             | 得到新的观察，不保证现场未变化       |
| 精确文本文件写入         | 比较完整文件内容             | 文件等于预期内容                     |
| 下载                     | 稳定目录、完整文件、终端回执 | 本地下载完成；不等于网站数据全部正确 |
| 任意 Shell、点击、提交   | 无终端回执时待复核           | 不自动推断外部操作未发生             |

当前实验验证进程结束与容器重启，没有执行整台物理宿主机断电。持久化文件的原子替换也没有被宣称为跨任意存储故障的绝对保证。

## 7. 网关与票据

- Web、网关都验证真实拥有者会话；只有 worker 能接触 Docker。
- 票据绑定拥有者、会话、agent、观看/控制模式、epoch，30 秒过期，只能使用一次。
- 票据通过 WebSocket 子协议传输，避免出现在 URL 查询参数与常规 URL 日志中。
- 网关校验 Origin，原子领取票据；异步连接上游后再校验一次，防止接管竞态。
- 待连接的客户端也进入撤销集合；交接中收到的输入不会在上游连好后被补发。
- 会话每两秒复核，退出登录会关闭已有桌面连接。
- 从 0.8.1-dev 起，网关把拥有者 WebSocket 的二进制字节经 Docker exec stdin/stdout 送至容器内 loopback VNC：观看 5900、控制 5901。工作站/观看容器均不发布桌面端口；观看容器使用 network=none。网关使用 Docker 自有传输，worker 无需加入 guest 网络。云端同域 WSS/Compose/HTTPS 仍待 P7 实测。
- task JSON 通过显式字段投影返回控制摘要，绝不返回 `connection_secret`。

早期版本等待 Colima 的发布端口转发，曾出现 Private control relay did not become reachable。0.8.1-dev 移除了该发布和探测路径；新连接使用受信任内联 Node TCP relay，stdin EOF 关闭远端 socket，断开时回收本地 CLI。双向背压限制慢观看者造成的排队。该变更消除了对宿主转发的依赖，旧次失败的 Colima 内部原因仍未定位。

升级需排空旧任务，停止并移除本安装的 guest/viewer 容器，保留 home/profile，随后按同一镜像重新创建。已有发布端口的 guest 或网络配置不符的 viewer 会在启动前被明确拒绝，不沿用旧暴露配置；系统层与内存现场按冷重建规则处理。数据库仍为 0011，镜像仍为 0.2.0 / guest 协议 2。

### 7.1 本次传输证据

- `test:docker-stream`：一 MiB 二进制往返、stdout EOF 后非零退出传播、断开后远端 relay 与本地 CLI 无残留、缺失容器错误。
- `test:transport`：真实 Docker/数据库/拥有者会话，零发布端口、viewer 无网络、原始可输入 RFB 客户端仍只读、控制/按键释放、旧连接/票据撤销、三次重连清理、拒绝文本帧、退出登录，以及旧部署配置拒绝/显式重建。
- `test:desktop`：noVNC 实际画面像素、手机/桌面截图、接管/交还/实际取消；握手成功继续单独于画面可见检查。
- 配套模型恢复三组回归通过。没有重跑与传输无关的全量产品套件，真实模型判断和云网络隔离没有因此获得验收结论。
