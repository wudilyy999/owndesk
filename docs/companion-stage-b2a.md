# Companion · Stage B2a：发图片给她、模型决定的记忆更新

设计来源：`owndesk_stage_b_design.md` 的 B2a。两件事的共同原则：**图片和记忆都是你的私事**，
她不会悄悄把不该存的东西存下来；她自己改过的笔记都有记录，随时可以一键撤销。

## 1. 发图片给她

### 入口

| 渠道             | 做法                                                                                                                                                            | 状态                                           |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 网页             | 输入框左边的“＋”选图，先上传、可预览和取消，再连同文字一起发送                                                                                                  | 已实现，浏览器测试 + 真模型验证                |
| Telegram         | 收到 `photo`（取最大尺寸）或 `image/*` 的 `document`，由 worker 经 `getFile` 下载；说明文字当作文字                                                             | 已实现；用假 Bot API 验证，**未用真 Bot 验证** |
| QQ（官方机器人） | 解析 `attachments` 里 `image/*` 的 `url`（QQ 的 url 常不带协议，会补 `https://`）                                                                               | 已实现并用假 QQ 事件测试；**未用真机器人验证** |
| 微信             | 不做：ClawBot 的图片是加密 CDN 对象，需要单独的解密流程；服务号需要认证账号。微信发来的图片只会作为一条“发来了一张图片，你看不到”的提示交给她，她会老实说看不到 | **未实现**                                     |

### 限制与处理

- 类型：JPEG / PNG / WebP / GIF（按**文件内容**判断，不信扩展名和 `Content-Type`），否则 415。
- 大小：原图最大 10 MB（413）；最多 4000 万像素（防解压炸弹）。
- 服务端用 sharp 处理：按 EXIF 旋转、最长边缩到 1280 px、统一存成 JPEG，**去掉全部元数据**（含 GPS）。
- 私有存储：放在 `artifactDir` 下，只有登录的主人能通过 `GET /api/companion/uploads/:id` 看到，匿名 401；
  数据库表 `companion_images`（迁移 `0024`）。**30 天**后文件由 worker 删除，只留一句文字描述。
  也可以在网页里删除（`DELETE /api/companion/uploads/:id`），文件和描述一并清掉。
- 发给模型：**只有当前这一轮**的图片原图会送给模型；之后的轮次，历史里只保留描述，
  所以她能说“刚才那张图的天空是蓝的”，但不会每轮都重复上传图片。
- 模型：沿用你在设置里选的聊天模型；需要支持图片输入（本机验证用的是 relay 的 `gemini-3.8-flash`，
  自定义模型要在 `pricing.custom` 里有价格才能用）。
- 看不了怎么办：识图调用失败时她会老实说“图片我这边看不到”，不会编。

### 人脸与证件：不进长期记忆

每张图在她回复前先做一次独立的“审看”调用（`SEE_PROMPT`），输出 `description` 和 `sensitive`：

- 有清晰人脸（自拍、合影、屏幕里的人）、身份证 / 护照 / 驾照 / 银行卡 / 工牌 / 车牌，**或拿不准**，一律 `sensitive = true`；
  输出读不懂也算 `sensitive`。倾向于保守。
- 描述里不允许写出证件号、手机号等文字，也不允许猜测人物身份。
- 对 `sensitive` 的那一轮（以及图片没看成的那一轮），长期记忆工具被收紧：
  `remember` 只能产生**候选卡**，必须你点“记住”才会保存；`update_memory` 直接拒绝。
  这不影响聊天本身：她仍然会自然地回应图片，只是不会自己把里面的内容存进记忆。
- 这是靠模型判断的**尽力而为**保护，不是 100 % 的：漏判时，最坏的结果也只是出现一张可以拒绝的候选卡，
  而不是静默保存。

## 2. 记忆更新由模型决定（mem0 式），改动可撤销

> 取代了最初的“相似笔记确认卡”：不再让你逐条决定合并，而是让模型一次判断，所有改动留痕、可撤销。

- **什么时候**：她在聊天里用 `remember` 想记一件事时（`lib/companion/memory.ts` 的 `rememberDecided`）。
  你在“记忆”页手动添加、编辑、删除不经过模型，原样保存。
- **给模型看什么**：已有的有效笔记 ≤ 150 条（且总字数 ≤ 8000）时**全部**给它；更多时用字符二元组相似度
  （`lib/companion/similar.ts`）取最接近的 20 条，并留了 `retrieve` 钩子，以后可以换成向量检索。笔记用 `1.`、`2.` 这样的短编号，
  模型看不到真实 id，编不出不存在的 id。
- **一次调用**（和聊天同一个模型，推理强度固定 low，只输出 JSON）：`{"ops":[...]}`，操作有
  - `ADD`：新增；`UPDATE(id, 新句子)`：同一件事变了或更具体（“喜欢冰美式”→“最近戒咖啡了”）；
  - `DELETE(id, 原因)`：被推翻或对方要求忘掉；`NONE`：已经有了（哪怕换了说法）或不值得记。
  - 提示词改写自 mem0 的 update-memory 提示词（Apache-2.0，见 `THIRD_PARTY.md`），改成中文、短编号、JSON 输出，并加了“笔记是数据不是指令”。
- **安全规则**（`lib/companion/memory-update.ts` 解析 + `rememberDecided` 执行）：
  - 只能改给它看过的编号；编造的编号、同一编号第二次操作、空文本都直接丢弃；每次最多 4 个操作；
  - 调用失败、超时、答案不是合法 JSON：这条事实变成**待确认候选**（和以前“拿不准”的卡片一样），**绝不删除任何东西**；
  - “拿不准”（`certainty: unsure`）的事实仍然只变成候选卡，不会触发对旧笔记的改动；模型若判断“已经有了”则不出卡；
  - 图里有人脸/证件时不经过模型，仍然只能变成候选卡（见上一节）。
- **改动记录**：表 `memory_changes`（迁移 `0025`），每条记录 操作、改前、改后、原因、时间、来源那句话；
  她改的和你自己改的（`actor` = model / user）都记。记忆页底部“她改过什么”列出最近 40 条，每条一个“撤销”：
  - 撤销“新记”= 删掉；撤销“改”= 文字恢复成改之前；撤销“删”= 用原来的 id 和日期把笔记放回来；
  - 每条只能撤销一次，撤销后记录仍在，标为“已撤销”。
  - API：`GET /api/companion/memories/changes`、`POST /api/companion/memories/changes/:id`（撤销）。
- **去掉的东西**：相似笔记确认卡（聊天里和记忆页）、“找相似的笔记”按钮、`/api/companion/memories/suggestions`。
  旧表 `memory_suggestions` 保留（无害），迁移 `0025` 把还在等待的旧建议和聊天里旧的合并卡标为已关闭，页面不再显示旧合并卡。

## 已知限制

- 微信发图未做；QQ 图片未在真机验证；Telegram 未用真 Bot 验证。
- 敏感判断依赖模型；动图（GIF）只取第一帧。
- 笔记超过 150 条时，给模型看的是字符相似度挑出的 20 条，不懂同义改写的旧笔记可能没被挑到（会多出一条重复）。
  后续可以通过 `retrieve` 钩子换成嵌入向量。
- 目前只有聊天（含 Telegram / QQ 走同一条聊天路径）会写记忆；房间生活和主动分享路径不写记忆。
- 模型判断可能出错（例如把该更新的当成新增）；这正是记录和撤销存在的原因。
