本文补齐“用户安全提供秘密 → 授权使用 → 浏览器填写 → 中断核对”的完整流程。字段级实现落地后，用代码、定向检查和证据替换相应待验证项。

## 1. 先用一个例子解释

任务：“登录报表网站，下载上周销售数据。”

1. Agent 观察登录页，只得到页面地址和输入框编号，例如用户名 `r3`、密码 `r4`。
2. Agent 请求使用保险箱中的“销售后台账号”。模型得到的是 `itemId` 和脱敏提示。
3. 用户在已登录的网页看到：“向 `https://reports.example.com` 的这两个输入框填写账号和密码，仅限本次动作。”用户同意，或选择接管。
4. worker 核对当前页面、控制代数和授权，临时解密并发送给工作站；记录中保存账号条目编号和动作回执。
5. 浏览器报告两个字段已填入。是否登录成功要在后续页面单独核对；填入成功不表示账号有效。
6. 如果密码刚填入就断线，系统显示“填写结果未知，需要核对”，等待用户决定；同一授权不会再次自动填写。

这里有两个不同问题：控制面的记录能否避免存下秘密；秘密进入网站后谁能读取。前一个问题可通过接口、持久化边界和检查收紧。后一个问题受工作站信任边界限制，见下一节。

## 2. 明确的信任边界

| 位置                            | 允许接触什么                   | 产品边界                                                 |
| ------------------------------- | ------------------------------ | -------------------------------------------------------- |
| 用户的安全表单                  | 本次输入的明文                 | 同源、拥有者登录、HTTPS；不写草稿、URL 或浏览器持久存储  |
| Web / worker                    | 必要处理期间的明文、部署密钥   | 属于受信任控制面；日志与错误不得携带秘密                 |
| PostgreSQL / DBOS / 事件 / 对话 | 密文或条目引用、非秘密授权信息 | 不持久化秘密明文；密文备份和主密钥分开保存               |
| 模型正常工具上下文              | 脱敏条目、字段名、结果状态     | 不主动提供密码、验证码或支付信息的值                     |
| 目标网站 / 浏览器               | 被填入的值、登录 Cookie        | 网站脚本和浏览器可以读取或使用它们                       |
| 同一工作站中的 Shell / 代码     | 可能接触浏览器、文件和登录态   | 当前具有通用 Shell，无法据此保证对恶意模型代码的秘密隔离 |

**本方案提供控制面保密、显式授权与可核对的使用记录。它不提供对拥有同一 guest 代码执行能力的模型的凭据隔离。** 隐藏输入框、截图遮罩和禁止返回 `input.value` 都不能改变这一边界。

首次启用自动填写时，界面要说明：同意后秘密进入 Agent 的工作环境；用户可以改用接管。人工登录也会在同一浏览器留下登录态，不能宣称接管能隔离所有后续账号使用。需要更强隔离时，应单独验证受限执行环境或凭据代理；该分支不在本次自动填写链路中预建。

身份/支付信息沿用这一边界。授权卡片控制受支持的凭据工具，任意 Shell 和网页脚本仍可能产生其他效果；不得宣称它能硬拦截全部支付、发送或删除。

## 4. 数据与加密设计

### 4.1 复用已有表，补足必要字段

`vault_items` 已接入认证读写、安全请求与 login/code 自动填写。0010 已增加：

| 字段          | 用途                                               |
| ------------- | -------------------------------------------------- |
| `revision`    | 条目编辑递增，旧授权不能悄悄使用新值               |
| `origin`      | 用户明确允许的精确协议、主机与端口                 |
| `scopeTaskId` | 临时条目仅供提出请求的 Task 使用                   |
| `expiresAt`   | 临时条目和验证码的有效期                           |
| `consumedAt`  | 一次性条目已消耗自动使用权，未知效果也不能自动重用 |

保存条目无需复制密码到任务表。授权继续保存在 `task_requests`，动作继续保存在 `task_actions/task_action_attempts`。原 `vault_approvals` 可保留历史读取；新审批统一走 task_requests，不建立第二套决定权。

旧 `site` 保留原含义以便导入核对。尚无精确 origin 的旧条目要求拥有者重新确认，不能把旧通配范围自动放宽为新授权。条目删除后，历史动作的脱敏快照仍应可读；不把引用存在当作条目仍然可用。

### 4.2 加密绑定

继续使用现有 `MASTER_KEY`、随机 IV 和 AES-256-GCM。保险箱密文使用明确的新格式前缀，并以 `INSTALL_ID + itemId + kind + 格式版本` 作为 AAD 绑定上下文。

可以把 AAD 理解为密文的“行号封条”：把 A 账号的密文换到 B 账号一行，解密应失败。它不隐藏行号，也不防止持有主密钥的控制面解密。

现有 provider/Telegram 的 `v1:` 密文保持兼容；保险箱的新格式要求绑定上下文。格式错误、绑定不符或主密钥缺失直接报错，不降级为旧格式尝试解密。条目普通字段修改用 revision 失效授权；涉及绑定字段变更时明确重新加密。

0010 增量迁移已应用；旧临时条目按原创建时间补一天有效期。原 origin 未确认的条目继续不能自动使用。新建临时条目为十分钟、绑定 Task；leased worker 每五秒的现有维护批次清理过期、已消费或任务终止的临时密文。消费标记的实际填写使用已有 S4 受控证据。

## 5. F14-A：保存或临时提供秘密

### 保存条目

1. 用户在设置页输入，客户端只在当前表单内持有明文。
2. 专用拥有者 API 核对会话、Origin、条目类型、字段与允许的目标 origin。
3. 服务端生成/核对条目 ID，校验后加密，事务保存密文、版本与脱敏信息。
4. 返回白名单 DTO：ID、类型、标签、提示、origin、revision、有效状态。查询和编辑页不回传旧秘密；编辑秘密需要重新输入。
5. 出错时显示具体字段或错误类别，错误中不带提交值、完整请求体或原始网络 URL。

### `request_secret`

1. Agent 提交请求目的、种类和已观察到的目标；不让用户在聊天或 Telegram 回复密码。
2. 复用 task_requests 保存待填写请求。Telegram 只发认证网页入口，不接受携密答复。
3. 用户从专用表单选择已有条目，或创建仅本 Task 可用的临时条目。
4. **密文保存、条目引用回复、请求决定和 DBOS 唤醒在同一事务提交。** 明文不得进入通用 `respondToRequest` 的 response。
5. 相同表单请求键不新建第二个条目。重试时在安全 API 边界内解密已有条目，对比规范化提交；字段一致返回原引用，不一致明确冲突。临时明文只用于本次比较，不保存请求副本或明文去重记录。任务/请求已失效时拒绝提交。

现有 responder 自己创建事务，需要沿其调用链做最小调整以复用同一连接。只拆出当前凭据提交确实需要的事务内部分，避免创建通用审批框架。

## 6. F14-B：批准一次批量填写

模型可见输入示例；其中没有秘密值：

```json
{
  "itemId": "item-login-example",
  "revision": 1,
  "pageId": "page-example",
  "observationId": "observation-example",
  "fields": [
    { "field": "username", "ref": "r3" },
    { "field": "password", "ref": "r4" }
  ]
}
```

1. worker 从可信任务关系取得 Agent/工作站，不接受模型任意指定别人的工作站。
2. 查询条目可用性，核对当前控制、页面、精确 origin、字段白名单和可编辑目标。首条链路只支持主 frame；iframe、系统对话框或无法定位的场景转人工接管。
3. 保存 `purpose=vault_fill` 请求和授权快照：Task、segment、action、itemId/revision、origin、pageId、observationId、epoch、bootId、字段映射、有效期、payloadVersion。
4. 用户看到真实目标地址、条目提示、要填写的字段、用途和同 guest 的信任说明。普通填写只授予填入，不自动授予表单提交、支付或后续新任务。
5. 用户同意后，worker 再核对相同绑定。等待期间发生导航、条目修改、接管、重启或过期，旧授权失效，重新观察并生成新请求。
6. 同一有效现场下可继续原动作，无需让模型重新产生同一工具决定。批准后控制变化时禁止刷新旧授权的 epoch；完成动作的收尾例外不适用于凭据填写。

建议初始授权有效期为 5 分钟；验证码默认 10 分钟以内并允许用户缩短。这些是设计默认值，实际实现需在界面显式展示。永久条目也需要每次使用授权；不在首版增加站点级永久免审批策略。

精确 origin 由 URL 解析器标准化；默认只接受 HTTPS，显式限定的本机测试夹具可使用 HTTP。登录重定向到另一 origin 需重新确认，不能凭名称相似或子域关系放行。

## 7. F14-C：派发、填写和保存回执

当前普通工具链会持久保存参数：`executeAction` 写 task_actions.input，guest 的 `saveAction` 也写 operation.params。秘密直接走 `browser_fill.text` 会把明文写入两处日志，因此需要一个明确的敏感派发分支。

```text
持久化：条目引用 + 授权范围 + 动作 ID
                 ↓ 核对并消耗本次使用权
临时内存：worker 解密 → 现有 stdin 传输 → guest 填写
                 ↓
持久化：状态 + 已处理字段名 + 非秘密回执
```

实施约束：

1. DBOS 的步骤输入、返回和唤醒消息只含引用；解密发生在实际派发边界内。
2. 先保存本次派发意图和一次性消费状态，再发送。两者之间退出也不自动重发，允许一次额外人工介入以换取明确的使用边界。
3. 复用现有 Docker stdin 传输，不通过命令行参数、环境变量、剪贴板或临时明文文件传递秘密。
4. guest 敏感入口先分离持久化元数据与瞬时值。动作去重比较 ID/元数据，不把秘密放进 params、operations 历史、回执或日志。
5. 一批目标先完成可行性检查，再逐个填写；每次填写前重新核对页面和目标。第一项触发导航时停止后续输入，明确记录部分/未知结果。网页脚本可在检查后变化，不能承诺对恶意页面的原子填写。
6. 批次完成后作废原观察。现有单字段 `/fill` 会立即作废 observation，不能直接连续调用它来实现同一观察下的多字段填写。
7. 返回字段名和完成状态，不返回值、不自动附带截图。普通观察不收集 input.value；敏感路径错误按阶段和明确错误码输出，保留可排查状态，不转发可能包含值的原始异常。
8. 后续截图/网页可能显示已输入内容，必须按当前场景处理遮罩和提示；这属于减少意外暴露，不能解释成对 guest 的安全隔离。

## 8. F14-D：中断、失效与一次性消费

| 中断点                             | 恢复行为                                                 |
| ---------------------------------- | -------------------------------------------------------- |
| 用户尚未决定                       | 保留待处理请求；控制现场变更后请求失效，需新观察/新授权  |
| 已同意，尚未消耗派发权             | 当前绑定仍有效才可执行；重启后旧 boot/epoch 失效         |
| 已登记派发，尚无回执               | 查询已有回执；无法确认是否填写时进入复核，不再次发送秘密 |
| guest 已填写，宿主尚未保存结果     | 已知 guest 回执可采用；回执缺失/guest 更换时保持未知     |
| 宿主结果已保存，框架检查点尚未保存 | 返回同一非秘密结果，不解密、不再次填写                   |
| 一批只填写一部分                   | 展示已知字段和未知部分；后续动作需要新观察与明确授权     |
| 用户拒绝/取消或条目删除            | 拒绝新派发；已进入 guest 的值无法靠数据库回滚撤回        |

临时条目绑定 Task、过期时间和一次自动使用权。一次性验证码在派发前消费；结果未知也不自动解锁，通常请求新的验证码。消费后的密文由清理流程删除，历史仅保留引用和脱敏状态。未消费但已过期的条目也不允许继续填写。

持久条目可以在新动作/新授权中再使用。历史回放从来不构成新的授权。进程内明文应及时解除引用；JavaScript 内存管理不提供可证明的立即物理擦除保证。

## 11. 合理性判断

值得增加的部分都有对应窗口：瞬时传值防止普通日志保存密码；精确 origin 减少错站填写；动作级绑定防止旧批准移用；消费状态与回执处理重复输入；同事务提交防止“凭据已存但任务一直等”。这些机制可复用现有账本和请求链，不需要增加消息中间件或另一个 Agent 框架。

主要代价是每次授权、站点跳转时重新确认，以及未知结果时的人工核对。先用真实登录任务测量介入次数和成功率，再决定是否需要更宽的授权策略。对模型代码的秘密隔离需要另一个明确的执行边界，本设计不靠遮罩冒充这一能力。

期限界定为释放/派发授权期限；已放行的浏览器动作不承诺在截止毫秒前完成全部字段。同guest读源可以被Shell改写，来源一致性检查不构成防篡改或商户真实性验证。下一条纵向流程是S5-C的明确提交批准、未知效果复核与付款结果证据，不把S5-B选择/填写批准扩展为付款授权。

## 16. S5-C 实施作业：提交批准与结果证据（开发中）

固定上游项目的answerPayment在方式批准后让模型填写并完成付款，新实现保留完成支付的目标，同时把最终按钮派发单独绑定。复用原Task/request/action/DBOS循环，新增payment_submit与只读payment_result；不新增执行框架或依赖。

1. 填写已知完整回执后重新观察，payment_submit引用原paymentRequestId、当前page/observation、按钮r引用与商户/金额t引用。原选择和填写只证明准备完成，最终提交另建五分钟批准。原准备的资料密文可以已被临时清理，核对已存回执和冻结方式，无需再次解密。提交仍须同Task/segment/agent/origin/page/epoch/boot，当前商户/金额与原选择相等。
2. worker独立读取按钮tag/type/label/formAction/formMethod及页面原文，只支持主frame的可见可用button或input-submit，同站点form；iframe、外部form、CVV/PIN继续人工处理。批准卡明确站点、商户/金额、遮罩方式、具体按钮和期限；仅认证网页可批准，Telegram提供网页入口/拒绝/取消，不以普通文本授权。

4. guest在一次派发内再核对文本、按钮描述、origin/epoch/boot和期限后点击一次；点击开始后的错误统一为未知效果。已知guest/host回执直接复用，不再要求新批准或重复点击；未知复核仅继续/取消，不能人工点“完成”伪造付款成功。
5. payment_result独立读取当前四个不同t引用：商户、金额、状态、订单/回执编号。要求同任务的已批准且已标记提交，不能使用其他Task或仅方式选择；host保存和UI展示原始页面证据，标为page_text_only。页面及读取器同属可修改guest，状态文字不等于银行/商户后台已核销；缺字段/跨站/金额不符明确转人工核对，不猜成功。
6. 候选0.12.0-dev/SQL0012/工作站0.5.0/guest5，先隔离验收，不升级主服务0.8.1/0011/guest2或改旧F12/网络/资源镜像。先跑具体提交/结果/未知窗口和受影响原支付准备；后续按覆盖扩大，保留所有原案例数量门槛。
