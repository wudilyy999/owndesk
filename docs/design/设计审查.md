## 1. 当前判断

**在“单人自托管、拥有独立电脑、需要跨会话长任务和中断恢复”这一目标下，当前架构合理，适合继续完成端到端产品验证。**

合理性来自目标与机制对应：现有界面和桌面可以复用；执行状态迁出请求进程；同一浏览器降低现场切换；结果核对补上执行结束与实际交付之间的差距。

尚不能据此宣称：一定比 上游项目 更快或更便宜、任意网站都可自动化、所有副作用都恰好发生一次、Docker 对任何攻击都绝对隔离、任何大模型都能可靠操作桌面。这些说法超出了当前证据和系统边界。

## 3. 本轮纠正的设计缺口

### R01 队列串行不足以证明桌面无冲突

旧命令或浏览器动作可能在原运行结束后仍继续。设计补上 workstation_control、epoch、在途动作检查和实际进程回收。epoch 只阻止旧请求，停止旧进程仍需工具或容器层的动作。

判断：该增加有直接依据，属于真实系统边界问题。首版用单 worker 和明确隔离流程解决，不引入分布式锁平台。

### R02 取消工作流不足以证明取消了真实操作

用户可能已取消页面请求，但命令继续写文件。F06 要求停止新派发、回收进程、核对结果后才标 cancelled。无法清理时隔离/停止工作站，保留成果与未知效果说明。

判断：需要作为发布条件；仅检查任务状态字段会漏掉根因。

### R03 接管必须在服务端形成控制权交接

前端 noVNC 的 viewOnly 可以被客户端改变。F05 使用服务端只读入口和有范围的控制连接，交还后关闭旧连接，再恢复 Agent。

判断：这是云端自托管必需的边界。增加两个私有 VNC 入口可能有资源代价，应测量，避免自行解析整套 RFB 协议。

### R04 任务和工作站不能永久绑成同一个执行单位

原有顺序 Agent 交接会切换执行身份和工作站。设计增加执行段：业务 Task 保持不变，换工作站时结束当前段并入队下一段。第一条流程只用一段。

判断：为保留现有交接能力而增加的最小划分；不扩展为通用图编辑平台。

### R05 结果核对必须表达验证强度

报表日期和字段可以程序检查，研究结论通常无法靠格式检查证明。设计记录程序检查、模型复核、人工确认和未验证项，完成条件需要和交付承诺一致。

判断：能提高可信度，但必须克制“全自动验证”的表述。文件正确生成不等于业务内容全部正确。

验证器应由控制代码维护，并在工作站之外检查提取后的成果。模型能修改的脚本或完成标记不能独自决定验收结论。

### R06 复用越多，迁移依赖越要透明

SQLite 同步访问贯穿设置、provider、server actions 和 worker；原有 localhost 桌面地址也不能直接给手机使用。保留 UI 不代表这些边界无需修改。

判断：最大化复用值得做，但不能为维持旧接口而增加同步阻塞或双重运行时。迁移按纵向调用链逐步完成。

## 4. 最薄弱的四个地方

| 薄弱点     | 可能出现的实际问题                           | 决定性证据                     |
| ---------- | -------------------------------------------- | ------------------------------ |
| SDK 组合   | 文档有接口，但所选依赖版本或连接方式不兼容   | G01 的原子提交与恢复实验       |
| 浏览器共享 | profile 被两个进程占用、人工导航让旧引用失效 | G02 的交替操作与重启实验       |
| 控制与取消 | 用户操作时旧输入仍继续、旧控制连接可再输入   | G03 和 T07 的实际输入/进程检查 |
| 外部副作用 | 提交成功但记录失败，恢复后重复执行           | G04 的确定断点实验             |

这些实验应优先于大范围界面和业务功能开发。实验失败时调整对应边界，不需要推翻已经验证的其他模块。

## 5. 简单方案与当前方案的取舍

| 方案                       | 优点                                  | 当前目标下的代价                                       |
| -------------------------- | ------------------------------------- | ------------------------------------------------------ |
| 在原 上游项目 加若干状态表 | 迁入最快、部署轻                      | 需自己实现恢复、等待和队列一致性，错误窗口更难统一处理 |
| 已选 DBOS + PostgreSQL     | 原生执行账本与队列，TypeScript 可延续 | 引入数据库与确定性的步骤约束，初期集成工作更多         |
| 全面换语言和 Agent 框架    | 能采用另一生态                        | 重写 UI 边界、provider 和工具协议，当前没有验证收益    |

因此保留已选技术方向，同时把 G01 作为继续投入的条件。并不需要为了“新版”再替换已能工作的桌面、UI、消息格式和模型适配。

## 6. 对用户有意义的“先进”

用同一任务比较以下结果：

1. 完成的成果是否符合约定，是否指出未验证内容。
2. 发生中断后，已完成工作能否保留，是否产生重复结果。
3. 用户需要介入几次，接管是否顺畅，是否发生输入冲突。
4. 重复任务是否正确使用上次规则，是否少走重复步骤。
5. 已知费用、总耗时、资源峰值和恢复时间。

能在这些指标上证明改善，就有实际产品价值。框架数量、使用新语言或代码重写比例本身不构成优势证据。

## 7. 当前可以接受与尚不能接受的结论

可以接受：这是一个围绕明确任务设计、尽量复用现有模块的可行原型方案；技术接口有官方依据；主要错误窗口已被列入流程与验收。

尚不能接受：生产级稳定、跨任意网站通用、固定低配服务器资源承诺、固定性能倍数、绝对不重复外部操作、任意工具自动审批完备。这些结论需要范围更具体的实验，部分保证本身也超出了外部系统可观察性。

G01—G04 与模型执行最小链路已验证。接下来完成真实模型任务与保留功能，完成 Telegram 的真实网络验收，推进凭据、剩余保留功能和部署；基础记忆已进入新执行体系，相关性检索与规则复用继续验收。

目前保留已选架构，控制与恢复边界已有实际证据。Shell 冷重建会丢失系统层与内存态现场，这是首版明确接受的代价；如真实任务频繁受影响，再用指标评估限制 Shell 权限或改变隔离方式。

## 9. 当前合理性判断（2026-10-25）

**值得继续实现。** 四个关键机制已有运行依据，暂时无需再换语言、执行框架或数据库。

具体例子：下载完成后、业务回执尚未保存时结束 worker，恢复后仍只有一份下载；
网站已记录提交却没有回复时，恢复会停下来请用户复核。这样的区别正好对应长期个人任务的实际需求。

本轮同时推翻了一个过弱的验收口径：VNC 显示“已连接”不能证明能看见桌面。
加入画面断言后发现跨容器截图黑屏，修正后才接受 UI 结果。

当前方案的主要成本是 PostgreSQL、独立 worker、每个桌面的只读 sidecar，以及 Shell 使用后的冷重建。
这些成本换来了明确的恢复和控制边界。是否在完整体验上超过参考项目，仍由真实任务、人工干预、资源与费用的同条件对照决定。

## 10. 模型链路落地后的追加审查

新增的模型回执解决一个真实窗口：模型已经回复并被业务表保存，DBOS 步骤尚未落盘。受控恢复实验已证明此时无需再次生成。未知请求则等待用户同意，代价是保守的人工介入；该取舍符合个人长期任务的费用可控目标。

新增记忆沿用原表和工具名，只增加与事件同事务的回执。它避免恢复时把后续已忘记的笔记重新写回，暂时无需向量库。

核心多轮会话已通过受控检查。当前最明显的产品缺口：真实模型判断与剩余聊天管理尚未验收；Telegram 文字入口已落地，真实网络及更多联动仍需验收；月预算与费用核对已有受控证据；五种例程已有受控证据；完整费用视图/保险箱/顺序交接未全部迁入；云部署和同条件对照尚未完成。

另一个需要直说的边界：高风险 ask_user 目前依赖提示词选择何时调用。任意 Shell 和网页点击的语义尚无完整强制审批，不能宣称所有付款/发送/删除都被系统硬拦截。

结论：**技术机制有实证，继续实现合理；“整体可用性超过 上游项目”仍是一项待验收目标。** 当前没有测得支持换语言、换数据库或增加大型 Agent 框架的必要性。

## 11. 多轮会话落地后的判断

继续沿用原 threads/messages 与聊天展示是合理的；新的任务执行边界没有要求另造一套聊天协议。每轮仍有独立目标、预算和交付，历史快照解决“刚才那个文件”的指代，同时排除失效工具引用。线程锁和明确轮次避免竞争提交交叉，已有 23 个实际轮次的受控证据，其中一次取消按终止记录保留。

新增浏览器请求键持久化直接对应已受理响应丢失的真实窗口，网页重载后仍复用原任务。字符预算仅约束历史快照，不代表整个请求一定适配所有模型的 token 窗口；小上下文本地模型仍需真实联调。完整工具输出、语音和对话管理尚未全部迁入，真实模型与整体对照目标继续保留。

## 12. 设计包一致性复核（2026-10-25）

本次按拥有者阅读与开发交接场景重新检查，修正四处会影响实际实现的表述：

1. F01 统一为部署端一次性创建拥有者，公开注册始终关闭；删除与当前认证设计冲突的网页初始化凭证流程。
2. F04 明确未知模型请求需要用户授权后再次调用，并保留费用不确定性；文件恢复核对约定内容、完整性和动作回执，完成标记不独自证明交付正确。
3. 架构图和 F05 明确独立只读 sidecar，观看授权不依赖 Agent 能修改的工作站进程。
4. 详细设计 7.1 明确混合通道的选择与切换规则；可能已生效的动作先核对，通道超时不触发另一通道的盲目重做。

新增[方案总览](方案总览.md)，用同一个报表任务解释复用、工具选择、恢复、接管、交付与下一阶段。迁移说明增加真实旧数据的隔离演练、正式切换和回退作业单，明确导入器尚未实现。

**审查结论保持：架构与目标匹配，关键机制已有受控证据，继续采用合理。** 实际产品是否超过参考项目由真实模型、保留功能、部署恢复与同条件任务结果判断。本次仅修改文档，没有把设计校验计为应用功能或重新运行完整应用验收。

## 13. Telegram 落地后的判断

复用上游命令和配对体验，保留普通 fetch 客户端与现有格式模块是合理的；无需增加另一个 bot SDK 或 Agent 框架。新增 inbox 是为覆盖“任务已提交、游标未推进”的真实窗口；新增 outbox 是为表达 Telegram 无幂等发送回执时的未知效果。

8 组受控检查已支持配对隔离、收件重放、多轮答复、版本回调、实际停止和未知发送的设计。渠道错误不会停掉桌面控制循环，已有 webhook 显式报告冲突。代价是通知最多等待一次长轮询，未知发送会要求人工核对；目前不能承诺即时通知或端到端恰好一次发送。

当前继续完善渠道联动、费用视图、凭据和部署合理。真实模型、真实 Telegram 网络、更多控制联动与同条件 上游项目 比较仍是独立完成条件。

## 14. 费用与月预算落地后的判断

逐次账本有直接依据：单个逻辑决定无法准确表达跨月重试、未答计费和每次价格快照。新增记录只负责请求计费证据，继续由 DBOS 恢复执行，未创建第二套工作流引擎。

设置月预算时暂时串行付费模型请求，是首版可接受的取舍：短事务检查累计费用与在途记录，HTTP 不持有全局锁；其他任务可取消，本地模型继续。将来只有实际吞吐数据表明受限，再考虑有依据的费用预留。

单次调用可能令总费用超过剩余额度，未知费用需要用户账单核对；界面和示例准确说明。历史记录不按新单价重写，人工核对和 provider 回执分开。金额边界、时区、并发、恢复和实际界面已有受控检查，继续采用当前实现合理。

真实模型、真实账单、完整费用视图和例程联动仍是后续验收条件；该阶段不改变整体超过 上游项目 的同条件比较要求。

## 15. 例程设计的合理性与取舍

继续采用上游计划类型与现有 Task/工作站队列合理，无需增加 Celery、Redis 或另一套 Agent 框架。业务运行先冻结、再以稳定键提交，覆盖了真正会重复交办的断点；日历计算交给已有 PostgreSQL，避免 Node 进程时区决定计划含义。

单一 DBOS 调度器相比每条例程一份框架 cron，减少计划更新与漏跑策略的双写。代价是约 30 秒粒度和持续心跳元数据。当前五种配置都以分钟为最小输入，该粒度与单拥有者日常任务匹配；发布前仍需实测长期数据库增长、积压速度及清理策略。

独立对话让忙时任务可入队，一次性受理后可明确停用；代价是相邻周期的聊天不自动串联。重复报表仍要保存明确的输入/输出引用和经过核对的比较依据，“只在指定变化时通知”现已由宿主比较程序决定，受控证据见第 16 节；真实数据来源仍需核对，不能只接受模型写一句“无变化”。

新建计划目前缺少浏览器持久创建键，网络响应不明时应先核对列表；手动运行已有请求键和版本检查。历史分页、自动刷新、完整自定义合同编辑属于明确的剩余产品工作。

**结论：当前调度边界与首版目标匹配，保留现有技术组合合理。** 本轮只按已执行实验登记证据，真实模型、云端长期运行和同条件 上游项目 对照继续保持独立验收。

## 16. 条件通知设计的合理性

把通知规则放在用户冻结合同、把计算放在宿主验证器，与当前恢复/控制边界一致。比较继续复用 CSV 检查、成果提取、Task 完成事务和 Telegram outbox；没有增加数据库、消息服务或通用规则框架。

## 23. 完整恢复后的合理性判断（设计稿 1.14）

**继续沿用现有架构合理，F12 的受控 Linux ARM 范围已有完整证据。** 两台独立 Linux 内核/空目标引擎间恢复全库、成果、home/profile、固定镜像与密钥后，原文件可下载、秘密可解密、新浏览器任务可使用原登录态，两个未知任务保持等待。没有为恢复另建任务框架或数据库。

真实发现的问题比“恢复成功”更有价值：Shell 已提交 POST，随后收到 SIGTERM，旧代码仍当作成功推进模型。统一回执分类修正 guest 和 cached-host 两个入口后，提交及该任务模型调用均为一次。这说明持久化记录还需表达中断语义；仅保存终端结果不足以判定外部业务完成。普通非零退出没有被一概阻断。

当前取舍清晰：停机快照有写入停顿、约 3 GB 固定镜像包和同架构限制，换来简单一致的恢复集合；原安装离线、会话/控制失效、例程与渠道暂停，换来恢复点后外部效果的人工核对窗口。文件认证不加密 Cookie/数据库，存储介质需加密。未来有真实 RTO/容量压力后再考虑增量或在线备份。

证据边界仍保留：Cookie 为受控 profile 预置，grant 探针为样本，旧票据专门延长以检查拒绝，外部服务在目标重建；完整填密未在恢复后重测。实际 VPS/ACME、跨架构、普通公网 DNS、策略篡改生命周期与长期容量没有通过结论。下一项推进这些部署门槛，再补保留功能与真实模型/同条件对照，整体目标保持进行中。

## 24. 网络单项放行与完整部署保持分开

## 25. 资源实测后的最小调整（设计稿 1.15）
