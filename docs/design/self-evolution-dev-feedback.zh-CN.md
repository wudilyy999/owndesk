# 自改进开发计划：让 Agent 在改代码时验证效果

基线：OwnDesk main `81755f9`。阶段 1、2 已在 `feat/self-evolution-dev-feedback` 实现，尚未发布；阶段 3 单独交付。

一次改进沿用现有流程：收到需求 → 在实验室编辑源码 → 按需验证并修正 → 从最终提交构建候选 → 独立评测 → 主人采用。开发自测用于找错。采用资格仍由独立评测决定。

## 怎样选环境

从需求中写出一个可观察的结果，再选能观察它的最小环境。Agent 可以提出需要的检查，控制器只开放预设操作。同一项功能可逐级补证据；不按文件目录硬猜，不增加业务任务类型。

| 必须观察的结果                   | 最小环境                                         | 示例                                                       |
| -------------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| 输入经代码处理后的输出           | 现有实验室和指定单测                             | 短对话不触发摘要，超窗后仍保留最近纠正的原文               |
| 用户操作之后真实显示或保存的内容 | 候选源码 Web，按需配临时数据库和浏览器           | 两天各有一篇日记，筛选其中一天，只出现对应条目             |
| 队列、调度、恢复或文件产出       | 临时数据库 + 隔离 Worker；需要观察界面时再开 Web | Worker 重启后同一任务继续，结果文件只有一份                |
| 平台投递、真实桌面或版本切换     | 使用对应的专用验收环境                           | 依赖未提供则标记未验证；维护现有保护路径和真实推送授权规则 |

## 阶段 1 · 先把已有工具接成短反馈回路

沿用 `lib/evolution/reformer.ts` 的 `run_check` 和 Git 检查点；提供只读差异视图，覆盖本轮基线到当前编辑（包括尚未存成检查点的修改）。开始前记下预期结果，检查后记录实际结果、代码版本和证据引用。报告区分已通过、失败、未验证，后续修改使旧结论标为旧版本。先用一项纯逻辑改动验收：能从失败改到通过，期间不启动 Web、Worker 或数据库。

## 阶段 2 · 一个按需启动的网页预览

这是首版最重要的增量。沿用缓存的实验室镜像、合成数据和浏览器操作；让可信控制器在隔离内网启动读取本轮源码的开发 Web。保留编辑容器现有隔离，不挂生产数据卷、宿主 Docker 接口，不使用真实渠道凭据。浏览器操作仅对本轮预览开放；独立评审的判定接口不交给开发 Agent。

第一次需要时启动，同轮修改后复用环境；验证时确认页面已加载最新源码。取消、失败、重启后的清理都按本轮标识进行。4 核 8 GB 默认同时只开一个开发预览，正式候选构建前先释放它。Git 提交与工作记录由现有控制器保存，预览的合成数据允许丢弃。

验收只用一个完整例子：日记日期筛选先暴露错误，编辑后在同一预览重试并通过；中间不构建发布镜像。关闭预览，从最终 Git 提交构建候选，并由独立评测复核同一用户行为。记录冷启动到首次可操作、再次编辑到可复验的时间及内存峰值；不预设未经测量的速度承诺。

## 阶段 3 · 给后台改动补上真正的运行验证

先实现一个场景：用合成任务进入可恢复检查点，中断隔离 Worker，重新启动，再核对任务 ID、最终状态、文件及副作用回执。复用已有工作流和恢复测试；重启动作只能作用于当前测试实例。验收要求同一任务继续、文件可读且只有一份、模拟通知没有重复。只看到网页提交成功不能判定任务恢复通过。

范围：本计划不新增 IDE、通用容器编排平台或社区分发功能。开发入口沿用改进实验室；现有候选验收、版本采用与自动回退沿用原链路。

## 首版实现与复验

- 改进轮次按需调用 `view_diff` 和 `preview_web`。预览每次从对应 Git 源码读取，复用同一临时数据库和浏览器容器。源码改变时只重启开发 Web 并重新载入源码；预览中不构建发布镜像。数据库、Web 和 Chromium 共享一个只有回环接口的网络空间，不映射宿主端口。
- 版本由本机控制器记录。开发自测按源码树标识保存；页面展示最近 24 条自测记录、期望和实际结果，早先源码的结果标记为旧版。候选是否可采用仍由独立评测决定。
- Linux Docker 复验入口：`node --import ./tests/setup-env.mjs --import tsx tests/dev-feedback.ts`。先验证逻辑测试由失败变为通过且不启动预览，再用真实 Chromium 和合成数据库验证日记筛选。加 `--release` 会另外构建测试候选的正式 Web/Worker 镜像，使用全新数据库核对同一个筛选结果，然后清理测试镜像。本用例不会采用或部署候选。

2026-11-21 本机 Linux Docker 实测：纯逻辑用例先失败再通过，期间没有预览容器。浏览器填写日期并点击筛选：第一次实际读到三篇日记，修正后只剩当天的一篇；两次使用相同容器 ID，第二轮改进未能抢占预览，关闭后该安装没有预览容器。该次首次观测 31.4 秒（包含对失败结果的等待），源码更新后复验 16.0 秒。三个预览容器各自内存峰值之和约 1.84 GiB，只代表该次预览的上界，不含编辑容器、生产服务或构建进程。宿主并非专用 4 核 8 GB 机器。

发布路径复核也已通过：从修正后的测试候选提交构建正式 Web、Worker 镜像，在全新库运行迁移，用新合成账号登录正式 Web，独立确认目标日期的日记存在、其他日期的日记不出现。此项覆盖构建与业务结果，未触发真实模型或采用生产版本。
