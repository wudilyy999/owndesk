## 原完整产品规划（基础交付后继续）

首版面向一个拥有者、一台 Linux 云主机、一个 worker 进程。允许配置多个 Agent，各自使用专属工作站；同一个工作站的动作串行执行。

首条验收任务是：

> 从指定网站下载上一完整自然周的报表，合并文件，与上周比较，检查日期和字段，只在出现指定变化时通知用户。

它必须能展示浏览器现场，允许用户接管登录，保存成果，并在三个代表性中断点恢复或明确要求复核。首版不会把全部外部操作都宣称为可自动恢复。

第一批实现先使用可控网站、已知答案的报表和固定模型响应。运行机制通过后再调用真实模型、接入用户选定的网站。

## 如何知道这个设计合理

本包采用三层证据：

- **已核查**：上游源码实际存在的能力、官方文档提供的接口。
- **设计决策**：我们选择的模块边界、数据字段、交接和恢复规则。
- **待实验**：选定版本能否组合运行、并发与断电行为、真实网站和部署成本。

当前运行证据支持事务入队、共用浏览器、服务端控制和代表性中断恢复四条关键链路。真实模型效果、云部署、长期资源成本和完整产品可用性仍需后续验收。实施级控制流程及实际代价见代码工程 docs/control-protocol.md，本目录保留详细设计基线。

**本轮审查结论：保留现有技术栈，提前云端部署验证，按证据完成剩余产品能力。** 最小 Linux 私有部署与恢复演练不等待费用图表、复杂记忆或顺序交接全部完成；公网开放和发布候选仍须通过安全及产品门槛。理由与具体放行条件见《设计审查》第 19 节、《实施与验收》的 P7 与第 3 节。

## 对上一版计划的关键细化

1. 区分业务任务与执行段：一个任务可以换 Agent 或换工作站，换工作站前必须重新排队。
2. 工作流取消与实际进程停止分开处理，取消成功不能仅以框架状态为依据。
3. 观看与控制在服务端区分；人工接管要等待 Agent 的在途动作真正停止。
4. 恢复按“可重试、可核对、无法确认”处理动作，任意 Shell 不默认安全重试。
5. 对一般报告明确验证级别，文件与引用检查不等同于证明所有文字事实正确。
6. 首版升级默认排空旧执行段，避免同时实现多版本 worker 和复杂代码重放兼容。
