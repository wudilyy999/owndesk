## 2. 迁入方法

1. 固定提交并记录版本，不跟随变化中的 main 直接开发。
2. 先列出目标模块的导入关系，迁入实际需要的依赖，保留原目录与导出名称。
3. 先让复用模块在原含义下工作，再调整唯一的存储、执行或网络边界。
4. 每批只完成一个可验证纵向流程，不一次改完全部文件后才尝试启动。
5. 已替换的旧入口删除或停止注册，不让新旧 worker、定时器和 polling 同时运行。

源清单记录字段：原仓库、提交、原路径、新路径、处理方式、改动原因、验证编号和许可证。该清单随代码变更更新，不以文件数量代替实际复用质量。

## 4. 数据库迁移流程

### M01 先迁最短调用链

先完成 Agent 列表和详情：schema → 数据访问 → server action/query → 页面。确认类型、日期和空值行为，再迁设置、对话、消息等其他实体。

SQLite 同步调用改异步时，provider 工厂也可能受到影响。例如 `createModel → getSetting → DB` 原来同步读取，新版先异步得到配置再创建模型。不要只替换 db/index.ts 就假定其余调用可工作。

### M02 字段映射

| 上游语义  | 新存储                        | 校验                             |
| --------- | ----------------------------- | -------------------------------- |
| 字符串 ID | 保留字符串及业务唯一约束      | Agent/消息关系不被重编号打断     |
| 毫秒日期  | 明确 UTC 时间戳或受控数字表示 | 浏览器、服务器时区变化后显示一致 |
| JSON 文本 | JSONB                         | 消息 parts 和工具结果可以往返    |
| 布尔/枚举 | 对应 PostgreSQL 类型与约束    | 不静默把非法值变为默认           |
| 金额整数  | 保留整数单位                  | 计算和展示一致，未知金额保持未知 |

每个实体使用固定样本验证读写往返、关联删除和唯一冲突。不新增通用 Repository 层，只将已有操作改为明确的异步函数。

### M03 事务入队的例外边界

业务 CRUD 继续通过 Drizzle。任务写入与 DBOS 入队使用一个显式 node-postgres 事务连接，范围仅限该提交边界。不要把 Drizzle 内部私有对象当稳定 API，也不要在事务提交前等待工作流结果。

## 5. 运行时迁移流程

### M04 保留工具与消息协议

先列出旧工具 schema、消息 parts 类型、UI 卡片和 Telegram 标签的对应关系。迁入后保持这些形状，适配新 ActionResult 时在一个明确入口转换，避免每个组件各写一套解释。

### M05 抽出成熟处理逻辑

从旧 runtime 抽取已有上下文整理、图片兼容、工具结果压缩和最终文本处理。对固定输入输出做回归验证，不顺便改模型默认行为和整个提示词。

### M06 替换生命周期

Web 请求创建任务和订阅事件，不能再注册旧 Run Map 执行入口。worker 启动 DBOS、工具执行和 Telegram。例程触发统一走任务入口，旧 startRoutines 定时器停止注册。

迁移结束后检索运行入口，确认模型调用、定时器、polling 和工作站清理都只有一个负责位置。

## 6. 桌面与网络迁移流程

### M07 保留镜像并替换浏览器入口

先用原工作站构建验证截图、键鼠、文件和 profile。然后让 Playwright 接管 browser 命令及桌面启动器；同一 profile 不允许被原 Chromium 启动脚本与新控制进程同时打开。

优先保持原浏览器配置和目录。若更换浏览器构建，先备份 profile，再验证登录、下载和重启行为；不能直接把用户真实 profile 当实验数据。

### M08 将 localhost 连接改为认证入口

原 screen 组件的交互保留，desktopAccess 改为请求观看/控制票据及同域 WSS 地址。不要把容器内的 localhost 地址直接返回给手机。

工作站地址由 worker 按 Docker 网络和标签解析。Web 不获得 Docker socket。Caddy 代理桌面路径到 worker，worker 完成身份、资源和模式校验。

### M09 迁移接管和取消

保留原有卡片和“交还说明”，状态来源改为 task_requests 与 workstation_control。按钮显示与实际权限一致：服务端尚未确认停止时显示“准备接管”，不能先把 noVNC 切成可输入再停止 Agent。

## 7. 凭据迁移

复用输入校验、字段映射、脱敏函数和 AES-GCM 行绑定思路。部署密钥使用本工程显式稳定配置，适应 PostgreSQL 与容器迁移。站点范围改为拥有者确认的精确 origin，原子域匹配不直接迁入。模型 key 与 Telegram token 已有加密存储；保险箱 S1/S2 存储与安全提供已有受控证据，自动填写继续按 F14/T18 实现。

新部署创建一次主密钥；存在密文时密钥缺失应失败。备份同时包含数据和独立密钥，但保管方式分开。

旧用户数据导入需要另行取得：原数据库、对应密钥和原部署标识。只有原密文能够成功解密并验证样例后，才迁入新密钥体系。无法解密时要求重新配置，不尝试静默覆盖或猜测。

### 7.1 保险箱的具体迁入顺序

1. 固定上游 vault 校验/提示与表单样本，先适配 PostgreSQL 安全保存和脱敏查询。新密文绑定安装/行/类型/格式，现有 provider/Telegram 密文继续原版本读取。
2. 为旧条目补充显式 origin；没有确认的条目保留为不可自动填写，用户核对后启用。新设计不保存 CVV，导入旧卡片时明确去除并记录该处理。
3. request_secret 改用专用表单，在一个事务内保存密文、引用回复、请求决定和持久化唤醒；普通聊天/Telegram 回复不作为敏感输入接口。
4. vault_fill 保留工具名，参数变为条目引用、page/observation 与字段→ref 映射。取消盲焦点/坐标直接填密的默认链路，无法定位时转接管。
5. 复用动作意图/回执，增加瞬时值分支。不得把秘密交给当前会保存全部 input/params 的通用 browser_fill；guest 入口、错误和动作日志一并适配。
6. 先通过 login/code 的 T18，再迁入 identity/card/upi 与支付请求。旧 vault_approvals 不获得新执行决定权；历史脱敏记录可保留。
7. 有新工作流分支或 guest 协议变化时排空旧任务、备份并同时升级对应 worker/镜像。实际版本与 SQL 编号在实现时登记，本轮仅更新设计。

迁移完成证据包括五种条目/请求分支、安全表单、精确授权、一次性消费、实际填写、未知效果与日志检查。只有表单或 schema 迁入不能标记保险箱完成。完整信任边界与步骤见凭据与授权设计。

## 10. 迁移完成标准

- 复用清单中的模块有实际路径、来源和验证编号。
- 所有数据库调用链完成异步迁移，旧 SQLite 不作为可写后备存储。
- 运行、调度和 polling 没有双重启动入口。
- 原有保留能力使用新任务及认证机制。
- 桌面、浏览器和人工接管使用同一个工作现场。
- 失败、等待与不明确结果可以被用户看到。
- 模块级与阶段级验收通过，未通过的事项明确列出。

### M11：在隔离环境导入与核对

1. 从备份恢复只读来源，创建空的目标 PostgreSQL；如果目标已有业务数据，明确报错，首版不做隐式合并。
2. 运行目标 schema 迁移，创建新部署拥有者。旧本地数据的归属在导入时显式映射到该拥有者，旧会话和桌面票据不迁入。
3. 按外键依赖导入实体，保留 Agent、Thread、Message 和文件间的稳定关系。消息 parts、金额单位、布尔值与日期使用 M02 的明确映射。
4. 已结束的旧对话保留为历史。旧内存 Run Map、正在执行的 Shell、旧审批与旧工作流位置不转换为新 DBOS 执行记录；需要继续的工作由用户根据现场明确创建新任务。
5. 旧秘密先用旧密钥验证解密，再以新主密钥写入。逐项记录“迁入 / 要求重新配置 / 无法验证”，不把空字符串写成成功结果。
6. 恢复 home/profile 副本，确认浏览器单实例、版本兼容、文件可读和登录状态；Cookie 恢复失败应提示重新登录。
7. 例程先保持禁用，Telegram 不启动 polling 和补发通知。待时区、身份配对与漏跑规则核对后再启用，避免导入时触发旧任务。
8. 记录实体数量、主键/外键、JSON 往返、消息顺序、金额与时区显示、文件清单及秘密可用性。仅记录实际检查结果，不伪造旧成果验证级别。

导入失败时保留错误与当前隔离副本，修正原因后从空目标重新演练。迁移脚本使用已有数据库库和显式事务；当前范围不需要双写服务或通用 ETL 平台。
