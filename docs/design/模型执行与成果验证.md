## 1. 先用一个任务理解整个系统

用户交办：

> 打开报表网站，我来登录；你下载 10 月 12—18 日的数据，整理成 CSV。文件必须有 date 和 amount 两列，交付前给我确认。

系统按以下流程工作：

```text
网页提交目标、日期和检查条件
  → 数据库一次提交任务、第一条消息和执行队列
  → worker 读取任务快照并取得专属桌面
  → 模型决定“打开网站”，先保存决定
  → 工具打开同一个有界面浏览器，保存动作回执
  → 模型请求人工登录，持久化等待
  → 服务端停止自动输入，开放拥有者控制
  → 用户登录、填写交还说明
  → 撤销旧控制连接，截图并重新观察页面
  → 下载并处理文件
  → worker 在容器外检查实际 CSV
  → 用户确认交付
  → 保存成果、最终消息与完成事件
```

其中模型负责选择下一步；worker 负责授权、控制、记账和检查。固定模型测试替换的是“如何选择下一步”，HTTP 请求、数据库、Docker、浏览器和下载仍走生产实现。

## 2. 三种持久化记录分别解决什么

| 记录                                | 类比         | 保留的事实                                               |
| ----------------------------------- | ------------ | -------------------------------------------------------- |
| DBOS 步骤                           | 工作进度本   | 哪些步骤已经返回，下一步从哪里继续                       |
| task_model_decisions                | 模型请求收据 | 第几次请求开始过、回答是否保存、已知用量与未知计费       |
| task_actions / task_action_attempts | 工具派发收据 | 哪个动作派给哪个桌面、是否收到终端回执、外部结果是否明确 |

它们存在不同的提交窗口。例如模型已经回复、业务回答已保存，进程可能在 DBOS 写完步骤记录前退出。恢复后先读模型收据即可复用回答，避免又发一次请求。

这是一套工作流和相应的业务回执。业务回执只核对真实请求与效果，不实现另一套通用调度器。

记忆修改没有容器外部效果：在同一个 PostgreSQL 事务里修改 memories 并保存 task_events 回执即可，不额外创建一张记忆执行账本。

## 3. 配置与任务受理（F02）

### 3.1 拥有者设置

1. 拥有者登录后配置 provider、API 地址、密钥、默认模型和步骤上限。
2. 密钥用稳定 MASTER_KEY 加密后落盘；读取接口只提供脱敏值和配置来源。
3. 本地数据库设置优先于环境变量；删除本地值后环境配置可能重新生效，界面展示来源。
4. 自定义地址只接受 HTTP/HTTPS，拒绝 URL 内嵌凭据、查询参数和片段。
5. API mutation 校验会话与 Origin；Web 进程仍不访问 Docker。

设置支持继承的 11 个 provider 适配器；当前受控端到端证据覆盖 OpenAI-compatible 通道。其他服务的参数差异、图片和工具兼容性仍需逐家联调。

### 3.2 接收任务

1. 解析目标、完成条件和预算。
2. 先按拥有者、来源、clientRequestId 查找旧任务；参数一致直接返回原 ID。
3. 新任务检查 Agent 和模型配置。
4. 取得 Agent 名称、职责、指令、拥有者时区和相关记忆快照。
5. 同一事务写 tasks、thread、初始消息、segment、accepted 事件与 DBOS 队列。
6. 提交成功才返回 202。网络响应丢失时，客户端使用原键重试。

模型标识和指令保留受理时的快照，provider 凭据在发请求时读取。密钥轮换可以影响后续请求，旧密钥不写入任务历史。

**例子：**用户点击两次“交给 Agent”，两次携带同一请求键，只得到一个任务。第二次携带不同日期且沿用旧键，服务端返回冲突，避免悄悄改变原任务。

## 4. 一次模型决定（F03）

代码入口：`worker/model.ts`。

### 4.1 请求前

1. 根据 taskId、segmentNo、decisionNo 查询模型回执。
2. succeeded：直接使用保存的回答；不再调用模型。
3. pending：上一次可能已计费，建立 model_retry 请求，等待拥有者授权。
4. retryable 或首次请求：检查控制权，取得本次实际凭据快照。
5. 锁定任务，确认未取消，保存 pending 意图与 model_started 事件。

### 4.2 请求中

- AI SDK 只获得工具 schema，没有 execute 回调。
- 一次 generateText 只生成决定；工具由后续独立步骤执行。
- 使用安装版本要求的 instructions 参数；不把 system 消息混进普通消息数组。
- 保留上游上下文压缩和 provider 图片适配。
- 一个回答中的全部 tool results 先连续回填，再提升截图消息，保持工具协议次序。
- maxRetries 为 0。进程中断、超时或报错均不会在 SDK 内静默发第二次请求。
- 活动请求绑定任务取消信号及单次超时。

### 4.3 请求后

1. 规范化文本、工具调用、消息和 token 用量。
2. 用与本次 HTTP 请求相同的凭据快照脱敏，覆盖错误与响应字符串中的实际 API key。
3. 保存 succeeded、结果、估算费用和 model_decision 事件。
4. DBOS 步骤返回可序列化的回答；下一步骤才开始执行工具。

该脱敏处理保护实际 provider key。网页密码、截图、浏览器 Cookie 和用户主动写入的秘密仍属于私有数据，不能据此宣称所有敏感内容都自动识别和清除。

## 5. 模型请求恢复窗口（F04）

| 退出时间                        | 已知事实                 | 恢复动作                 |
| ------------------------------- | ------------------------ | ------------------------ |
| pending 写入之前                | 尚无已登记请求           | 按正常步骤发起           |
| pending 之后、回答保存之前      | 可能调用并计费，回答未知 | 等待拥有者同意再次请求   |
| 回答保存之后、DBOS 步骤保存之前 | 回答已存在               | 复用业务回执，不重复生成 |
| DBOS 步骤保存之后               | 框架已有结果             | 重放读取步骤结果         |

恢复可能改变桌面 epoch。即使模型回答可复用，回答内的旧动作也可能已过期。执行入口拒绝旧代数，随后获取新截图让模型重新决定。

**例子：**模型决定点击“导出”，随后 worker 重启。已经保存的决定无需再次付费生成；桌面重建改变了现场，旧点击不会直接执行，新截图会进入下一次请求。

用户同意再次请求后仍保留 uncertain_attempts。未知计费不会因为重试成功就变成零。

## 6. 工具执行与控制（F03/F05/F06）

1. 校验工具名和 Zod 参数；非法参数返回明确工具错误。
2. 检查当前 task、控制模式与决定绑定的 epoch。
3. 外部工作站动作先登记稳定意图和派发 ID。
4. guest 保存终端回执；恢复时核对回执与实际效果。
5. 已有明确结果可复用，未知提交进入复核，任意 Shell 不自动重试。
6. 接管或暂停使同批次剩余决定失效；旧引用不会继续使用。

工具优先级在提示词中约定：文件/计算用 Shell 和 fs_*，网页优先 DOM，视觉任务用截图与键鼠。这里没有固定的“50ms/100ms”承诺，实际耗时包含网络、模型、网站和执行时间。

### 人工等待

ask_user、request_takeover、预算和执行复核统一写入 task_requests。用户决定提交后，通过持久化消息继续任务；等待不持续占用模型请求。

接管：停止自动输入 → 确认可控边界 → 允许人工控制 → 用户交还 → 撤销旧连接与残留按键 → 重新观察。

worker 在人工等待期间重启，不应重新生成已保存的决定，也不应夺走人工正在使用的桌面。最新 CUA 检查已覆盖该路径。

### 取消

取消请求同时中止正在进行的模型 HTTP 请求并停止真实工作站边界。请求停止与任务标记 cancelled 分开处理，控制 worker 负责核对停止和框架取消。

### 审批的当前强度

当前 ask_user 可以持久化用户确认；高风险行为的识别与发起确认仍依赖模型遵守提示词。Shell 与任意网页点击具备广泛能力，尚无覆盖所有发送、付款或删除的语义级硬拦截。发布时必须明确支持的强制审批范围，不能把提示词规则包装成完整权限沙箱。

## 7. 长期记忆（F11 的第一步）

### 模型工具

- memory_write：保存一条最多 2,000 字符的独立笔记。
- memory_forget：按 ID 删除当前 Agent 的笔记，无法删除其他 Agent 的笔记。
- 写入/删除与动作回执同事务，恢复读取原回执。
- 控制代数变更时尚未执行的记忆修改失效。

**例子：**第一步写下“喜欢英文周报”，第二步用户改成中文，Agent 删除旧笔记。若之后框架重放第一步，读取原写入收据即可，不会把已经删除的英文偏好重新创建。

### 用户管理与使用

- 设置页提供查看、添加、刷新、逐条忘记。
- 新任务加载最近 30 条笔记，累计最多 12,000 字符。
- 任务保留受理时快照；任务中的最新记忆工具结果更新当前语义，后续任务重新读取数据库。
- 笔记落在自托管数据库，选入上下文的内容会发送给所选模型服务。
- 删除影响未来任务，历史任务快照保留。彻底清除历史副本需要单独的数据保留/删除功能。

当前使用确定的近期选择规则。相关性检索、规则冲突合并和通用流程学习继续列为后续验收，不提前添加向量数据库。

## 8. 成果提取与核对（F08）

代码入口：`worker/artifacts.ts`。

1. 模型调用 complete_task，提供摘要和文件清单。
2. worker 将路径限制在 guest home 范围内，从容器复制归档流。
3. 在宿主读取归档目录信息，只接受单个普通文件；拒绝链接、目录和多对象。
4. 使用 tar 的标准输出读取文件，不将容器提供的路径解包到宿主目录。
5. 限制归档输出和单文件大小，单文件上限为 20MB。
6. 根据用户完成条件核对 CSV：列名、重复表头、行数、真实日期与范围。
7. 不通过时返回具体原因，模型可在预算内修正。
8. 通过后按服务端生成的稳定 ID 保存成果及元数据。
9. 如要求人工确认，等待确认后保存最终消息与 completed 状态。

### 验证强度

| 显示内容        | 证明什么                       | 尚未证明什么                         |
| --------------- | ------------------------------ | ------------------------------------ |
| 文件已提取      | 已从容器取得实际字节           | 数据来源与业务事实                   |
| program_checked | 声明的字段、行数、日期检查通过 | 源网站数字真实性、遗漏记录、业务结论 |
| human_confirmed | 拥有者确认当前交付             | 所有外部事实均由独立系统复核         |
| model_reported  | 模型报告完成                   | 独立事实正确性                       |

**例子：**CSV 的 date/amount 两列齐全且日期正确，但 amount 数值由模型编造，结构检查仍可能通过。需要来源核对的任务应增加与原始数据的比较器，当前界面明确显示来源真实性仍需核实。

## 9. 费用与边界

- 每次实际请求尝试记录用量；读取历史结果不重复计算为新请求。
- 单任务步骤上限控制下一次模型决定；接近上限时等待用户追加。
- 单任务费用上限基于已知估算；未知价格或可能已计费的尝试会请求用户处理。
- 定价目录从固定上游迁入，金额是估算，真实账单以 provider 为准。
- 月预算配置项已保留，月度强制额度与完整费用界面尚未实现。
- 费用字段目前为整数，发布前需核对极大自定义价格与上下文量的存储上界。

## 11. 这部分设计是否值得保留

**当前判断：值得保留，复杂度与已暴露的故障窗口相对应。**

- 独立 worker 防止网页断开影响任务。
- 业务回执覆盖框架检查点之前已经发生的模型请求与工具效果。
- 同一浏览器减少 DOM、视觉和人工之间的登录现场切换。
- 容器外检查阻止模型自行给自己的成果盖“验证通过”印章。
- 记忆沿用 PostgreSQL 与原有 schema，避免先引入一套检索服务。

主要代价是 PostgreSQL 运维、每桌面的观看 sidecar、Shell 冷重建、保守复核带来的介入次数，以及尚未完成的产品功能。真实模型成功率、资源与人工介入对照，决定这些代价是否划算。

## 12. 多轮对话与追问的实现（F13 / T17）

### 12.1 对话与任务的关系

Thread 保存长期沟通入口，Task 保存一轮具体目标和执行边界。例如先生成 report.csv，再追问“金额翻倍”，会形成同一 thread 中的两个 Task，各自保留预算、成果、状态与模型用量。第二轮不修改第一轮的验收结论。

### 12.2 受理与历史快照

- 请求可携带 threadId，必须属于当前拥有者和所选 Agent。
- 受理事务锁定 thread，再检查活跃任务，分配 thread_turn，写消息和入队。
- 不能仅按 created_at 推断轮次：PostgreSQL now() 是事务开始时刻，竞争事务的开始时间和实际受理次序可能不同。
- 历史快照保存近期原始用户目标、最终助手回复或终止状态、已解决人工问答及成果路径/验证等级。
- 最近最多 50 轮，按完整问答对控制在 64,000 字符。被省略的轮次明确告知模型，相关内容需要用户补充或另行检索。
- 未完成/取消任务可能已经产生外部效果，后续任务需检查当前现场，不能把终止当成“从未执行”。
- 回答旧审批和操作旧截图不构成新权限；新轮次使用新的控制现场与完成条件。

### 12.3 已受理但用户没收到响应

假设服务器创建第二轮任务并提交，网络随后断开，网页显示提交失败。浏览器已在请求前保存完整参数与 clientRequestId，草稿也仍保留。用户刷新并重试时携带原键，服务端返回已经存在的任务，不创建第三轮。

当前保证覆盖同一浏览器标签会话的重载。新的浏览器会话不一定具有原本的本地请求键；用户应先查看服务器已有任务。浏览器草稿属于私有本地会话数据，不能当作服务器记忆或跨设备同步。

### 12.4 成果与显示

第二轮模型从上下文得到 report.csv 的工作站路径后，仍需实际读取文件。即使覆盖 guest 中的同名文件，第一轮成果已经复制到可信存储，旧下载保持原内容。聊天中分别显示历史成果和当前轮次的任务控制。

Transcript 复用原有消息布局与滚动依赖，Composer 复用键盘/IME 与草稿行为；Markdown 和导出格式也来自固定上游。服务器执行继续使用任务 API/SSE，网页不接管模型生命周期。

### 12.5 具体证据

- runtime-chat.json：23 个生产工作流轮次，包含一次取消；同线程追问、修改已存在文件、旧成果不变、并发互斥、拥有者/Agent 隔离、问答等待重启和有序历史分页。
- runtime-ui.json：真实网页提交、受理响应丢失与重载复用、草稿保留、重命名/导出、任务地址持久化及手机界面。脚本没有执行，远程图片没有自动访问；加入实际滚动位置断言后，重载能看见最新回复。
- thread.test.ts：完整问答裁剪、不受后续源对象改动影响、取消效果提醒和继承导出格式。

这些证据依然使用受控 provider。真实模型是否理解“刚才”的指代、能否正确重算真实报表，继续作为实际任务评估内容。

## 13. 逐次模型用量与月预算（0.5.0-dev / T12）

### 13.1 为什么增加 attempts

一个模型决定可能先请求失败或中断，再经用户同意重试。task_model_decisions 仍保存逻辑决定与最终可恢复回答；task_model_attempts 为每次实际请求保存独立时间、模型、价格快照、用量和计费结果。恢复读取成功回答不会新增 attempt。

例子：10 月 31 日发出的请求没有收到回答，11 月 1 日经用户同意重试。旧请求保留在 10 月且费用未知，新请求在 11 月独立记账；最终回答保存在原逻辑决定中。当前月份由拥有者 IANA 时区计算，避免跟随服务器时区改变。

新记录的 started_at 取派发意图事务的时间；本应用的请求归档月份与服务商发票结算月份分别理解。0008 回填旧决定的尝试，原来没有保存的重试时间明确标 legacy，并按原决定首次记录时间归档。

### 13.2 一次付费调用的事务边界

1. 若已有成功决定，直接返回保存结果。旧未答请求先保留未知费用，等待重试授权。
2. 在短事务内取得共享费用准入锁，锁定当前 Task，核对取消状态。
3. 读取当前自定义价格和拥有者月预算，按同一数据库时间计算月份与累计成本。
4. 达到预算、当前模型无定价或本月有未核对费用时，保存 monthly 等待请求；不创建派发 attempt，也不发送模型 HTTP。
5. 月预算启用时，同一拥有者已有付费调用在途，其他任务短暂等待容量；它们仍可取消，不要求用户额外批准。
6. 放行后，在同事务保存模型意图、attempt、价格快照和事件。提交后才发 HTTP；不跨 HTTP 长时间持有费用锁。
7. 回答成功后，将逻辑回答、attempt 用量/费用和事件一起提交。失败或中断保留 unknown，不能把未返回费用写成免费。
8. worker 重启先将未完成 attempts 登记为未知；逻辑决定按原恢复流程处理。

月预算配置与自定义价格更新使用同一短事务锁。它解决并发请求同时通过费用检查的问题，不新建队列平台；代价是设置月预算后付费模型请求串行。本地模型不受付费容量约束。

### 13.3 预算含义与具体案例

- 留空无本地上限；0 暂停付费请求。清除本地值会恢复环境变量预算，环境值单独管理。
- 月预算按已知费用和人工核对费用控制；存在未知费用时暂停新付费请求。
- 假设预算 $10，已知花费 $9.99，下一次调用实际为 $0.02，完成后总额可达到 $10.01，之后停止新付费请求。系统无法提前得到该调用的服务商最终账单。
- 暂停任务可在拥有者调整预算/核对费用后重新检查。普通“继续”不绕过检查；条件仍未满足时生成新的明确等待。
- 到下一自然月，worker 对到期 monthly 请求以 calendar 身份自动重新检查；仍经过实际准入。停机后根据持久化期限补做检查。

### 13.4 未知费用核对与价格

用量页展示已知费用、在途调用、未知项、模型汇总和逐次明细。拥有者根据实际服务商账单填写未知请求费用（未收费填 0）与依据。人工金额单独保存，原 provider 结果与原价格不覆盖；修改也写入 task_events，能追溯前后值。

自定义输入/输出/缓存价只作用于以后调用。缺少用量或缺少定价的已返回回答仍可出现费用未知；后续添加单价不会伪造当时的已知费用。历史定价来自固定上游目录，界面注明它不是实时价格源。

金额使用 bigint 存储，边界拒绝负数、非有限值和不能安全表示的整数；模型响应 token 计数也在外部边界校验。该设计修复原 cost_micros 整数上界，不把金额溢出转换为 0。

### 13.5 当前证据与保留范围

4 个定向金额/日期/渲染检查；runtime-usage.json 覆盖 7 组受控结果：台北/纽约时区与 DST、两个真实工作站的费用容量互斥、零/耗尽/月中暂停、无定价与未知费用、人工核对、免费本地兼容路径、期限恢复、30 亿微美元存储、旧记录回填、手机/桌面 UI 和分页。分页使用明确标记的 53 条历史样本，不能称作 53 次真实模型调用。

runtime-recovery.json 重新验证成功回答不重生成、未知请求明确授权后重试，逐次账本没有破坏原恢复语义。模型服务响应受控，真实服务商账单对照仍待授权配置。完整趋势、按 Agent 汇总与例程费用联动继续迁入。

明细日期固定采用拥有者时区与 zh-CN locale；服务器渲染和不同浏览器时区/语言显示同一日期，避免跨月记录被本地浏览器时区误读。生产 UI 在拦截响应中复核，没有更改拥有者实际预算或费用。

## 14. 定时例程与冻结日期（F10 / T11）

### 14.1 先区分计划、一次运行和真正任务

“每周一 9 点整理报表”是一条可修改计划。2026-11-02 这一周的触发是一条不可被后续编辑覆盖的运行记录。实际调用模型和操作工作站的仍是原 Task；新增例程没有第二个 Agent 执行器。

```text
保存计划（v1、纽约、周一09:00）
  → DBOS 定时唤醒串行调度器
  → 锁定计划行
  → 冻结本次输入并保存 routine_run，同时推进 next_run_at
  → 原 submitTask，复用原来源键
  → 工作站任务队列
  → 模型、工具、人类协作、成果检查
  → 原 Task 链接和运行历史
```

计划修改得到 v2；已有 v1 的运行记录继续执行原输入。手动运行也先保存快照和来源键。暂停和归档阻止未来触发，已经受理的工作仍需从原任务取消。

### 14.2 两个断点如何恢复

| 中断位置                  | 数据中有什么                      | 恢复行为                                   |
| ------------------------- | --------------------------------- | ------------------------------------------ |
| 受理事务提交前            | 尚无运行，游标未推进              | 下一次扫描再次受理                         |
| 运行已保存，Task 尚未创建 | queued 运行、冻结输入、已推进游标 | 从 queued 补交 Task，沿用原键              |
| Task 已提交，运行回执前   | Task/DBOS 入队存在，运行仍 queued | submitTask 根据原键返回原 Task；不新建任务 |
| 运行已链接 Task 后        | 原 Task 及执行/请求回执           | 原执行恢复，例程只显示状态                 |

运行键由例程、计划版本和预定时刻组成。手动键保存于当前标签页的 sessionStorage；受理响应不明时刷新重试仍沿用该键。存储失败明确显示并停止新的交办。

### 14.3 日期、夏令时与漏跑

例子：纽约 2026-11-02 周报的“上一完整自然周”为 10 月 26 日至 11 月 1 日。这个星期跨越夏令时回拨，对应 169 小时。直接减去 7×24 小时会取错边界，所以由 PostgreSQL 在计划时区计算自然周，再保存明确日期及 UTC 区间。

日历计划的缺失时间顺延，重复时间取回拨后的一次；间隔小时按首次激活的 UTC 锚点推进。默认仅补最近一次，较旧触发合并登记跳过区间；skip 模式允许用户明确跳过超过 60 秒的过时触发。停机恢复后不创建一个月的心跳补跑。

### 14.4 明确的代价和后续验收

- 调度粒度约 30 秒，每次最多扫描 50 个计划、提交 50 条运行；这适用于首版单拥有者。大型计划量与长期心跳数据保留在 P7 测量。
- 每次运行独立对话，保证繁忙时可受理。跨周业务比较需引用指定文件或后续验证记录；当前没有自动建立报表比较流水线。
- 完成仍经原成果验证；Task 成功不自动证明业务结论正确。
- 例程页历史为最近 50 次，手动刷新。已有输入控件保留五种计划；squad/顺序交接后续迁移。
- 旧 SQLite 数据导入、真实 provider 与“仅指定变化才通知”单独验收，受控运行不计作真实模型效果。

## 15. 跨期报表比较与条件通知（0.6.0-dev / F08、F10）

### 15.1 用一个具体例子看边界

用户设置“每周一整理上一完整自然周，amount 合计增加至少 10% 才通知”。本期两份下载文件合计 330，基期两份合计 300。Agent 在工作站里下载和合并，完成时交付 report.csv 与 baseline.csv；worker 将两份文件分别提取到宿主目录，验证列名、日期及有效数值，然后独立计算 `(330-300)/abs(300)×100=10%`。达到含边界阈值，因此登记需要通知。

即使模型摘要写“没有变化”，程序仍按 10% 处理；模型写“变化巨大”而两期合计同为 300，on_change 依然保持安静。两种情况的原文件、程序决定与模型文字都能在网页分别查看。

### 15.2 冻结输入和真实执行顺序

1. 完成合同增加 comparison：基期 CSV 合同、数值列、absolute/percent、十进制阈值、any/increase/decrease、always/on_change。它由用户/API 配置，模型的 complete_task 参数不包含通知开关。
2. 例程的比较功能要求 previous_week 与两份 CSV 的日期列。本期按预定时刻固定上一自然周；基期的当地日历日期再前移七天。具体日期写入 Task 合同，恢复沿用。
3. Agent 通过原浏览器/文件/Shell 工具下载与合并。这一步继续属于模型工作，网站适配与数据合并真实性需要业务核对。
4. collectArtifacts 检查两份约定文件均已交付且路径不同，沿用已有普通文件、大小、目录和链接边界。分别保存宿主侧不可由 Agent Shell 修改的成果 ID。
5. 固定程序从宿主成果字节验证两个 CSV、读取指定列并求和。当前能力是一个数值列的合计比较，没有伪装成任意业务规则执行器。
6. 如需人工确认，卡片包含两份成果链接、程序比较和未经独立核实的摘要。等待期间修改 guest 文件不会覆盖已提取成果；退回修改走新的完成动作和成果 ID。
7. 最终 Task 完成事务同时保存 comparison、notification、结果及完成事件。提前取消仍按现有锁和停止边界处理；比较失败不会产生完成状态。
8. Telegram collector 只跳过“completed 且宿主决策 send=false”的完成通知。问题、预算、复核、失败和取消沿用原通知路径；未配置比较的旧任务默认通知。查询阶段排除静默任务，避免它们反复占据 LIMIT 队列。
9. 原 outbox 负责实际发送、回执、未知效果和显式重试。需要通知不等于已经送达，界面明确区分。程序合计先于模型摘要展示。

### 15.3 数值与异常定义

- CSV 数值只接受十进制：可带负号，整数部分最多 15 位，小数最多六位；不接受空值、NaN、指数、分组逗号、空白或隐式类型转换。
- 计算使用 BigInt 固定六位精度，JSON 和界面保存十进制字符串。百分比阈值通过整数交叉乘法比较，不依赖展示值的舍入；界面百分比截取六位小数。
- absolute 比较差额的绝对值；percent 使用差额绝对值除以基期合计绝对值。方向先单独核对；非零差额达到含边界阈值才 matched。
- 0→0 属于零差额；0→非零且采用百分比时，比例无法定义，登记 needsAttention 并提醒核对，不静默略过。
- 即便 minRows 配成 0，比较报表仍要求至少一行数值，避免把没有数据当成真实零值。
- 缺基期、错误日期、缺数值列或非法数值返回具体修正错误；不使用模型判断或默认零值替代。

### 15.4 完成标准与验证边界

检查需要覆盖四个真实定时任务：达到阈值、等值静默、遗漏基期后修正、零基期核对；浏览器实际下载多份源文件、Shell 合并、宿主比较、人工等待重启、原成果保留与 Telegram outbox 发送构成同一条链路。另以真实取消确认异常状态继续通知，并通过实际手机/桌面网页配置规则与下载成果。

数值单元检查覆盖 0.1+0.2、微小差额、含边界百分比、方向、负基期、零基期和无效数值。记录在 runtime-reports.json；受控模型和受控 Bot API 的证据与真实 provider、真实 Telegram 连接分别记账。

**能力边界**：程序证明输入文件上的结构、日期和数值计算，不能自动证明网站数据真实、下载完整、没有重复交易、币种/单位一致或模型文字正确。其他聚合方式、来源证明及完整性合同需按具体用户任务扩展，不写成已经覆盖。

### 16.2 授权填写的已实现边界

`executeVaultFill` 保存精确 grant，批准后使用原动作 ID 和原控制现场；`releaseValues` 在 Task/request/attempt 锁内检查条目和授权，以非秘密派发标记先消耗自动使用权，再临时解密。值经 stdin 的 transient 字段到 guest，宿主 input、DBOS 结果与 guest params 只保存引用/授权和安全回执。

guest 先核对全批目标，再逐字段重查并填写；导航、字段改变、部分超时转安全错误。填写不自动截屏；后续 DOM 观察与登录核对分开。已有 guest/host 回执可复用，条目被删除也不阻止读取历史结果；派发后无回执时仅继续/取消复核，不自动重复送值。

13 个实际任务覆盖密码/OTP、错站/过期/版本/描述变化、批准等待重启、guest 回执前后与框架检查点窗口、回执丢失、部分/超时和真实取消。网站匹配/计数、数据库/模型/日志样本值检查与任务数量门槛共同组成证据。受控模型/站点不证明真实模型规划或防恶意 guest 的秘密隔离。

## 17. 中断 Shell 回执与整机恢复（0.9.0-dev / F12）

具体失败：一条 Shell 已向受控服务 POST，随后 worker 强制退出，guest 保存 `signal=SIGTERM, exitCode=null`。旧 host 把“有终端回执”当作正常成功，让模型再次规划，产生第二次模型请求。外部提交无法靠退出码推定是否完成。
