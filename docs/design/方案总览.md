## 1. 一句话说明产品

**用户在自己的 Linux 云主机上部署一个长期运行的个人 Agent。它有自己的桌面、浏览器和文件，可以通过网页或 Telegram 接任务，按情况使用命令、网页结构化操作或截图操作，遇到需要人参与的步骤交还控制。**

产品定位延续 上游项目。新版优先改善任务中断恢复、结构化与视觉操作共用现场、人工接管、成果核对和重复任务执行。

首版交付范围和已实现范围分开：Telegram 文字入口已有受控证据；逐次费用与月预算也已有受控证据；五种时区例程已有受控证据；真实 Telegram、可信周期报表、保险箱和云部署尚未全部验收。准确进展见[实施状态](../STATUS.md)。

### 用户实际上怎样用

用户交办：

> 每周一上午 9 点，登录指定网站，下载上一完整自然周的销售报表，与前一周比较。销售额下降超过 10% 时通知我，附上 CSV 和三条说明。登录失效就叫我接管。

产品需要依次解决：记住规则 → 到点触发 → 打开已登录浏览器 → 下载 → 合并计算 → 检查交付物 → 按条件通知。关闭聊天页面不影响任务，worker 中断后按动作记录恢复。

这个例子贯穿后面的设计。这里描述目标闭环；真实模型、真实网站和完整周期执行仍需验收。

| -------------- | ------------------------------------------------------------------------------- |

## 4. 整体如何运转

```text
网页 / Telegram
    ↓ 验证身份、生成稳定请求键
任务受理事务：保存目标 + 历史/规则快照 + 入队
    ↓
独立 worker：取得该工作站执行权
    ↓
观察 → 一次模型决定 → 一个工具动作 → 保存回执
    ↑                              ↓
    └──── 未完成时继续观察和执行 ────┘
                    ↓
          人工等待 / 验证交付 / 失败说明
                    ↓
            保存成果、事件和通知状态
```

可以把它理解成三本账：

1. **任务账**：你让它办什么、当前状态、已经花费多少、交付了什么。
2. **执行账**：哪些模型步骤和工具步骤已有结果，重启时从哪里接着做。
3. **动作账**：某一次下载或提交是否真的发出、有没有回执、是否需要人核对。

DBOS 提供执行账。业务数据库保存用户目标和外部动作证据。两者有不同职责，避免再造一套通用工作流平台。

具体进程、数据表和授权路径见[详细设计](详细设计.md)，观看侧边界见[实现控制协议](实现控制协议.md)。

## 5. 用一次报表任务解释关键决策

### 5.1 登录和下载：为什么需要同一个浏览器

Agent 打开网站，发现登录失效。它停止自动输入，用户通过网页接管云桌面完成登录，然后点击交还。

交还后，Agent 重新观察同一个浏览器，继续用 DOM 找到报表按钮。Cookie、页面和下载文件处于同一工作现场，不需要在两个独立浏览器之间复制登录状态。

用户点下“接管”时，界面先显示准备中。服务端确认旧动作已停止后才开放输入。用户交还后，旧控制连接失效，Agent 丢弃旧坐标和页面引用。

### 5.2 合并与计算：为什么保留命令通道

两份 CSV 下载完成后，使用脚本解析日期、合并行和计算变化率。逐格打开表格、移动鼠标、复制数字通常缺少必要性。

如果网站按钮能够通过 DOM 稳定定位，使用结构化操作；如果目标只在画布里显示，使用截图与坐标操作。首版优先暴露现有明确工具，由模型在受控入口中选择，不为三条通道各引入一个大型 Agent 框架。

**通道切换有一个重要约束：已点击“提交”却没有回复时，不能因为 DOM 超时就再用视觉点击一次。** 先核对是否成功；无法确定则请用户判断。换通道不能绕过动作记录、预算或原有审批范围。

### 5.3 中途退出：为什么需要动作回执

假设第二份报表已经下载，worker 随后退出：

- 能找到完整文件与已有回执：采用该结果，继续处理。
- 只有半成品：按已定义的下载恢复规则处理，保留明确状态。
- 网站记录了提交，但本地没有得到结果：查询网站已有记录；查不到确定结论则等待用户。

恢复系统可以重用已保存结果。外部系统的未知效果仍需要核对。

### 5.4 用户取消：为什么不能只改任务状态

脚本可能仍在写文件，模型 HTTP 请求也可能仍未返回。取消流程先拒绝新动作，再中止在途调用、关闭控制连接并核对实际进程。

任意 Shell 可能创建脱离原进程组的程序。当前实现用容器停止/重建提供冷停止边界，保留 home/profile，丢弃系统层和内存现场。这让停止有可验证依据，同时带来重建与现场损失的代价。

### 5.5 交付：为什么文件生成后还要检查

Agent 写出 CSV，控制侧从容器提取文件，检查日期范围、列名和可读性。发现月份错误时，把具体错误交给 Agent 修正。

“字段和日期正确”可以程序检查。“销售下降是因为某活动效果差”需要业务证据，单凭 CSV 格式检查无法证明。最终界面分别展示程序检查、模型判断和人工确认。

### 5.6 下周再跑：为什么规则与例程要有版本

你说“这次临时只看最近三天”，只改变当前任务；你说“以后都以自然周为准”，才更新长期规则或流程版本。

定时触发使用例程 ID、计划版本和预定时间去重。停机漏跑后的补跑策略明确配置，避免恢复后连续执行一整月的旧任务。五种计划、时区/夏令时、漏跑和忙时排队已有受控证据；双期 CSV 宿主计算与条件通知也已通过受控检查，真实来源和模型另验。

## 6. 设计合理吗：逐项判断

**结论：在单拥有者、独立 Linux 桌面、长期任务和需要中断恢复的目标下，架构值得继续采用。** 已有机制证据支持继续实现，完整产品优势仍需真实任务对照。

| 决策                     | 对应的实际问题                       | 付出的代价                             | 当前判断               |
| ------------------------ | ------------------------------------ | -------------------------------------- | ---------------------- |
| 复用 UI、模型和桌面底座  | 避免重写已经存在的能力               | 需要处理原同步数据库与新执行边界的耦合 | 保留                   |
| Web 与 worker 分进程     | 页面关闭、请求超时不应终止工作       | 多管理一个服务进程                     | 保留                   |
| PostgreSQL + DBOS        | 提交一致性、等待与恢复               | 数据库运维和持久化步骤约束             | 关键机制已验证，保留   |
| DOM、Shell、视觉共用现场 | 不同工具之间保持账号、页面和文件一致 | 需要统一浏览器生命周期和观察版本       | 关键机制已验证，保留   |
| 服务端只读和显式接管     | 避免客户端开关决定输入权限           | 额外 sidecar、连接撤销和停止检查       | 保留                   |
| 单 worker、单工作站串行  | 降低同时输入和调度复杂度             | 人工等待会阻塞同工作站后续任务         | 接受首版上限           |
| 轻量记忆、顺序交接       | 先完成长期个人任务                   | 检索规模和并行能力有限                 | 按需要验收，不提前扩张 |

这套方案比“简单聊天 + 工具调用”更重，增加的部分分别对应已经存在的故障窗口。首版继续保持一个仓库、一个 npm 工程和一个 worker；向量库、插件市场、多租户和并行团队暂缓。

### 何时需要重新讨论技术选择

- 工作站排队与人工等待成为真实使用瓶颈：先测量阻塞来源，再讨论隔离或并发。
- Shell 冷重建频繁丢失必要现场：比较限制 Shell 权限、环境固化和更强隔离的成本。
- 当前记忆选择遗漏实际重要规则：先改善规则关联与检索，再判断是否需要向量库。
- 用户明确需要本机 Mac 应用：单独定义本机执行端、权限与同步边界。

当前没有验证结果要求全面换语言、换 UI 或增加第二套 Agent 执行框架。

## 9. 如何判断新版确实更好

固定 上游项目 提交、同模型与参数、相同任务、网站和初始账号状态。将两套产品分开部署，分别记录：

1. **交付正确性**：文件与约定结果是否正确，未验证内容是否说明。
2. **人工介入**：需要几次登录、澄清、纠错和接管，各自原因是什么。
3. **恢复**：代表性中断后是否保留成果，是否重复下载或重复提交。
4. **效率与成本**：端到端时间、模型调用/费用、CPU/内存和恢复耗时。
5. **可部署性**：干净 Linux 主机是否能按文档安装、备份、恢复与升级。

测试任务包括正常报表、登录失效、错误文件修正、已下载后退出、提交结果未知，以及多轮修改同一成果。记录每个任务的初始条件和各次结果，避免用一次成功演示外推稳定性。

只有同条件结果支持改善，才宣称对应能力超过参考项目。产品范围保留、机制检查通过、真实任务成功和整体可用性对照分别记录。

可直接执行的保留功能门槛、B01—B06 真实模型任务、C01—C06 指定故障/部署案例、记录字段及放行条件，见[实施与验收第 9 节](实施与验收.md#9-可用程度超过-owndesk的实际判定作业单)。它目前属于未执行的验收计划。

## 11. 首条条件通知的实现说明（0.6.0-dev）

用户给出两份 CSV 交付条件和一个求和列，例如“amount 增加至少 10% 才通知”。Agent 下载本期/基期多份文件并合并，宿主读取已提取成果重新求和。300→330 达到含边界的 10%，300→300 保持安静；模型摘要与决定相反时仍使用程序结果。

网页在成果确认、最终结果与例程历史中展示程序依据和两份文件链接。确认等待期间重启 worker 或修改 guest 原文件，恢复仍使用同一完成动作对应的宿主成果；旧 GUI 动作不会因此获得新控制权限。缺文件/非法数值不能以零值静默完成。真实源数据、文件完整性和单位一致性另行核对，具体证据见工程 runtime-reports.json 和 STATUS。

## 身份资料的复用示例（0.10.0-dev 候选）

例如“把我的收件信息填到这个站点”：模型读取脱敏条目编号，按观察到的姓名、邮箱、电话、地址控件请求一次批准；worker核对现场后直接在浏览器输入，模型不经过资料原文。缺邮编时整批明确拒绝，先补资料再授权；某一输入导致页面跳转时停止后续字段并请人核对。不会顺手点下单或付款。

本轮沿原账号/验证码链扩展identity，无额外框架/数据库，接着补卡片/UPI与支付确认。新guest3需与0.10应用配对，主服务尚未升级。详细验收结果看STATUS与分项证据，整体超过上游项目仍需真实任务与同条件对照。

## 支付准备的复用示例（0.11.0-dev 候选）

例如“替我准备这笔USD12.00的订单”：Agent先给出页面上的商店名/金额来源，你选保存的卡，再确认本次要填卡号/有效期等字段；网站在首字段之后改价，后续字段停止并请你核对。选择“我来处理”则进入实际桌面接管。批准若在慢页面读取中到期，解密前会拒绝，原值不再传入浏览器。

这些步骤复用已有保险箱、审批、控制和动作账本。支付准备15任务、原13回归、额外期限1任务已有受控证据，主服务未升级。页面和读取器同属可修改guest，文本核对不证明商家身份；最终点付款及结果核验留给S5-C。合理性和两次确认的代价见设计审查27节。

## 最终付款的受控例子（0.12.0-dev 候选）

例如“替我提交这笔USD12.00订单”：选方式、批准填写之后，再读取当前商户/金额与付款按钮，你单独确认最终提交。若确认后worker刚写完派发标记、尚未把点击发给浏览器就断电，恢复时会显示需要核对，继续也不补点。这避免重复支付，同时会让一笔实际尚未发出的付款停在人工处理。

同样，如果点击后订单号消失，或网站显示的金额变为USD13.00，结果读取失败，界面不会生成有效付款页面证据。marker和点击回执都不代表银行扣款；页面原文另列为page_text_only。原完整九任务和新增11边界任务已有受控证据，具体流程见凭据16.3/16.4。主服务仍0.8.1-dev/SQL0011/guest2；0.12/SQL0012/guest5只作为受控验收候选。真实模型/网站、财务服务与外部核销、候选Linux/云部署、剩余保留功能和同条件上游项目对照继续验收，S5/T18整体不标完成。用户已有云API/无费用上限授权保持，配置只通过本地设置。

## Agent顺序协作的例子（0.13候选）

你让A下载并处理CSV。A通过delegate把文件和说明交给B：若B正在处理另一任务，本任务显示排队，A已释放自己的桌面。worker保留一份宿主副本，B取得工作站后在Transfers新路径收到并核对同一文件，再继续分析。A原文件或B的设置后来被改动，不会悄悄替换这次已冻结的输入。

例如Task总额度只剩0步，B接手也会停在额度确认；交接不等于送一份新额度。交接中断后沿原标识恢复；取消排队中的这段，也不会停止B正在处理的另一任务。11Task受控证据见工程runtime-handoff.json。主服务仍0.8.1-dev/SQL0011/guest2，未应用0012/0013或修改原配置/拥有者。真实模型/服务、0.13 Linux/云部署、长期容量与同条件上游项目对照继续验收，整体目标保持进行中。云API/无费用上限授权保持，密钥只通过本地设置接入。

## 手机任务怎样安全交给另一个Agent（0.15候选）

例如手机入口A当前允许B接手。你发出任务后，收件记录已经保存B；随后你在网页改成C，即使worker在中途重启，旧消息仍交给B，下一条消息才允许C。这样重放不会偷偷换执行者。需要阻止旧代尚未受理消息时解除配对；已经创建Task则打开原任务取消。切换手机默认Agent或重新配对后，名单回到关闭，需要显式再选。

网页和例程已有的交接链继续复用；新手机3Task与原8组/5Task已受控通过。原squad团队配置/@成员、真实模型/Telegram及整体同条件对照仍需完成，详见模型执行第21节和工程STATUS。
