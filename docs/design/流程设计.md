## F01 首次部署和拥有者初始化

**输入**：Linux 主机、Docker、域名、拥有者设置。真实模型和 Telegram 凭据可以稍后配置。

1. 检查 Docker 和所需端口，创建明确的 named volumes 与私有网络。
2. 启动 PostgreSQL，分别执行认证和业务迁移，由 SDK 初始化其系统记录。
3. 首次部署在部署端配置独立主密钥；已有密文时保留匹配密钥，不重新生成。
4. 拥有者通过部署端命令创建账号；在一个数据库事务内核对首次初始化并保存账号。公开注册始终关闭，不开放网页抢占初始化入口。
5. 配置域名和 HTTPS，验证 API、成果、SSE 与桌面入口都受认证保护。
6. 添加模型配置，界面只返回脱敏状态；需要视觉任务时检查所选模型的图片能力。
7. 创建 Agent；首次使用时创建其专属工作站，展示明确的准备进度。

**失败分支**：数据库迁移失败则服务不进入就绪；主密钥缺失且已有密文时停止相关访问；工作站构建失败展示构建错误，保留数据库资料。

**验收**：外部访问不能创建拥有者；重复部署端初始化被拒绝；未配置模型仍可查看设置，任务提交得到明确配置错误。

## F02 交办任务、去重和入队

**例子**：“帮我整理本周报表”，用户连续点了两次提交。

1. Web 校验会话，Telegram 校验已配对身份；解析输入并取得稳定请求键。
2. 确定目标 Agent、工作站和基本交付条件。自然语言任务可在首次模型步骤补全细节；影响执行范围的歧义才要求用户澄清。
3. 从 PostgreSQL 池取得同一个连接并开始事务。
4. 按拥有者、来源、请求键查重/插入。若已有同参数任务，直接返回；不同参数返回冲突。
5. 写入任务、第一执行段标识和“已接受”事件。
6. 在该连接的同一事务中入队指定工作站分区。
7. 提交事务后返回 taskId 和状态；连接异常时按原请求键查询结果，避免生成新任务。

**失败分支**：事务内任一步失败整体回滚，用户收到明确失败；不能展示一个没有入队的“运行中”任务。

**证据**：业务行、入队记录、事件和请求键。G01 验证断开连接、重复请求和并发提交。

## F03 模型与工具执行循环

1. 队列允许本执行段进入工作站后，核对取消请求和工作站状态。
2. 检查旧控制连接和在途进程；取得当前 epoch，建立本段控制关系。
3. 读取已保存的配置快照、目标、相关记忆、已有动作结果和成果引用。
4. 获取本次所需观察。可以是文件内容、结构化网页信息、截图或已有可验证结果。按当前工作选用 CLI、DOM 或视觉工具；切换通道前核对上一次动作效果，具体规则见详细设计 7.1。
5. 执行单次模型请求，持久化最终输出、工具决定和用量。流文本仅作为展示增量。
6. 每个工具调用经过统一入口：校验参数 → 校验控制与当前状态 → 写动作意图 → 执行 → 保存回执及证据。
7. 更新 UI 事件和任务进度。需要登录或审批时进入 F05，达到预算边界则等待用户或按已约定方式结束。
8. 模型认为已经完成时进入 F08，不直接写 completed。

### 必要的拆分

```text
观察步骤 → 模型步骤 → 动作 A → 观察/核对 → 模型步骤 → 动作 B
```

不把多轮模型推理、十次网页点击和最终报告放到同一个持久化步骤里。工具函数尽量复用 上游项目，执行边界由新版管理。

### 普通错误

网络临时失败只对允许重试的动作进行有限重试。登录失效进入明确等待。无效参数返回模型可处理的结构化错误。预算不足停止新付费请求。任意外部副作用未知时执行 F04 的核对分支。

## F04 中断恢复与外部效果核对

**例子**：第二份 CSV 已下载，但回执尚未写入数据库，worker 退出了。

1. worker 启动并登记固定版本的执行定义，DBOS 找到可恢复执行段。
2. 读取业务任务和工作站状态，检查取消标志、旧控制连接和运行中的命令。
3. 工作站仍有旧动作时先等待、停止或隔离，禁止直接开始第二个输入序列。
4. 读取已完成的模型与工具步骤结果，重新建立进程内的浏览器对象和连接。
5. 找到最后一个结果不明确的动作，按下表核对。
6. 得到确定结果后更新动作记录；取得新观察，再继续模型循环。
7. 无法确定时保存现场和问题，进入 needs_review，通过网页/Telegram 只通知必要信息。

| 最后动作     | 核对方式                                         | 后续                                 |
| ------------ | ------------------------------------------------ | ------------------------------------ |
| 读文件/页面  | 重新读取                                         | 保存新观察，继续                     |
| 下载报表     | 找稳定动作目录中的完整文件，检查日期/列名/完整性 | 匹配则采用；半成品按既定下载规则处理 |
| 写报告       | 检查目标文件的约定内容、完整性与动作回执         | 满足约定则登记；不一致则复核         |
| 网页创建对象 | 用已有对象标识或页面历史查询                     | 确认成功则接续；无法确认则等待       |
| 任意 Shell   | 检查命令组、输出和明确的业务结果                 | 不能仅因没有回执就重跑               |
| 模型请求     | 有已保存最终结果则读取；未知请求保留计费不确定性 | 取得用户明确重试授权后才再次请求     |

**关键点**：旧截图的坐标、旧 DOM 引用、原来的焦点都不能当作恢复后的现场。重启可能保留文件和 Cookie，但不保证运行内存、窗口、下载连接完整保留。

**验收**：在“动作之前”“动作成功之后、记录之前”“记录之后”分别中断；结果必须符合分类规则。G04 覆盖最难的中间窗口。

## F05 登录接管、审批和交还

### A. 登录或用户主动接管

1. 记录接管请求，工作站进入 quiescing，停止派发新动作。
2. 等待在途工具完成或明确取消。核对相关进程组和输入；无法确认停止时隔离工作站。
3. 如需停止并重启容器才能清理残留进程，先说明当前未保存的现场可能改变；重新打开工作站后取得新观察。
4. 确认 Agent 输入停止后，递增 epoch，进入 human，签发有范围的控制票据。
5. 用户进入同一个工作站操作。界面刷新或手机断连不自动交还控制权。
6. 用户点击交还，可附“已登录”等说明。服务端记录决定并使旧控制票据失效，关闭实际控制连接。
7. 收到连接关闭确认后，递增 epoch，重新观察页面，再恢复任务。

### B. 普通审批

不需要桌面控制的审批仅保存任务等待。卡片展示具体目标、内容和参数版本。用户决定通过事务写入并发送持久化唤醒消息。

同一请求重复点击只产生一个决定；目标或参数变化后原决定不能复用。已过期或已取消请求返回明确状态。普通审批不自动开放 VNC 控制权。

需要提供秘密或使用保险箱时进入 F14。普通问答和 Telegram 文本不接收密码，填写批准也不自动授权支付或后续任务。

### C. 观看与控制

观看端由服务端强制只读。当前使用两个私有 VNC 入口区分观看和控制；观看服务位于独立只读 sidecar，避免 Agent Shell 修改工作站进程后改变观看权限。公网只访问经过认证的代理，代理根据票据选择入口。复用现有桌面组件，不自行编写 RFB 协议解析器。

控制入口只在 human 模式开放，票据绑定拥有者、工作站、epoch 和有限的握手有效期。已经建立的连接在交还、注销或服务关闭时被撤销。即使用户修改浏览器里的 viewOnly 属性，观看入口也不能输入。

G03 必须验证这个边界。两套 VNC 捕获带来的资源变化需要实测；若另一个经过验证的服务端只读配置更简单，可以替换，但验收标准不变。

### F05 桌面传输的已实现路径（0.8.1-dev）

1. 网页用原拥有者会话申请单次 watch/control 票据，网关消费票据并复核 epoch。
2. 网关通过 Docker exec 建立到 viewer:5900 或 guest:5901 的容器内 loopback 字节流；没有宿主发布端口，worker 不加入 guest 网络。
3. 网页 noVNC 继续接收 WebSocket 二进制 RFB；观看服务仍独立执行只读限制，前端设置不决定输入授权。
4. 接管、交还、退出或断连关闭字节流，stdin EOF 使远端 relay 关闭 socket；交还仍额外检查实际 5901 连接和释放按键。
5. 升级遇到旧端口/网络配置时明确停止准备，按迁移说明排空并重建，不在活跃现场自动换容器。

## F06 取消任务和回收控制

**目标**：用户看到 cancelled 时，已没有这个任务继续发出的受控动作。

1. API 幂等记录 cancelRequestedAt，立即拒绝后续新动作和新的付费模型请求。
2. worker 停止模型流读取、取消可取消的网络操作；模型服务是否停止计费依服务实际行为记录。
3. 关闭该任务的自动输入和控制连接，停止归属它的命令组。
4. 无法确认旧进程停止时，将工作站隔离；首版可以停止容器以结束残留进程，保留持久化数据。
5. 核对在途外部动作，记录“已发生”“未发生”或“无法确定”的结果。
6. 更新业务取消状态，结束/取消 DBOS 执行，确认可安全释放工作站后再允许下个任务进入。

框架的取消状态不能代替步骤 3—5。数据库故障导致取消决定尚未持久化时，页面不得宣称已取消；若可访问控制面，应先停止继续输入，并显示需要恢复核对的状态。

取消不会撤回已经发送的消息、删除已创建对象或撤销外部交易。已经产生的成果与相关证据保留给用户。

## F07 顺序交接给另一 Agent

**例子**：A 完成资料下载，B 接着分析。

1. 保存 A 的成果和交接说明；只传可持久化的内容与引用，不传 Page 对象或内存闭包。
2. 确认 A 没有尚未结束的工具输入，释放其工作站控制关系。
3. 在同一事务内，将任务的 activeSegment 更新为下一段，保存目标 Agent/工作站及上下文，并入队目标工作站分区。
4. 当前 DBOS 段正常返回；用户任务仍显示排队/交接中，不显示业务完成。
5. B 所属队列放行后，读取自己的模型配置、上下文和成果，重新取得观察并继续。

交接动作具有稳定 ID，事务已提交后重放不会创建第二段。目标工作站与原工作站相同时，新段等待旧段返回。不同工作站也必须通过其队列进入。

交接次数、用量和时间都计入原业务任务的总预算。首版保留顺序交接，不增加父任务占住一个并发槽等待多个子任务汇总的机制。

**当前实现**：0.13/SQL0013的11实际Task受控检查已通过，详见详细设计F07实现补充与工程runtime-handoff.json。准备事件先冻结目标配置/宿主文件，释放源后再以同事务创建段/更新Task/入目标分区；目标复制/逐字节核对文件并新观察。总预算和原对话入口保持，本轮owner名单约束发现/执行；例程名单入口在0.14、Telegram名单入口在0.15受控通过；原squad面板和真实模型另验。

## F08 结果验证和成果交付

1. 将完成条件与实际成果逐项对照。
2. 将待交付文件提取到受控位置，由 worker 的固定验证器执行确定检查：文件可读、日期范围、必需字段、约定的内容条件。Agent 自己返回“检查通过”只作为待核对信息。
3. 对文稿按约定检查格式、交付对象与来源；模型自检和人工确认单独标注。
4. 不通过且有预算的修正步骤重新进入执行；结果无法确认则进入 needs_review。
5. 通过后将完整文件提取到成果目录，记录稳定 ID 与验证结论。
6. 在事务内更新业务状态和完成事件，再由通知流程告知用户。

### F08 周期报表比较的落地分支

当合同含 comparison 时，当前 CSV 与基期 CSV 都必须交付，路径应不同。宿主按两份日期/列合同验证字节，独立计算指定列合计和变化。阈值含边界、方向独立判断，零差额不命中；百分比的零基期无法定义时提醒核对。完整规则与示例见模型协议第 15 节。

比较结果、通知决定与完成状态一起保存。网页显示程序比较和模型摘要；Telegram 只有在任务已完成且程序决定静默时略过完成通知，问答、复核、预算、失败和取消保持原入口。原 outbox 负责实际投递状态。

界面展示：做了什么、交付物、验证方式、仍需用户判断的内容。比如“文件日期和列名已程序检查；总结内容经过模型自检”，避免将两种检查混为一谈。

下载 API 只接受成果 ID，通过会话及归属检查后传输。若成果文件被意外删除，应报告缺失，不生成一个同名空文件冒充结果。

## F09 网页重连和 Telegram

### 网页

1. 客户端读取任务当前快照，记住最后事件序号。
2. 建立 SSE，服务端补发已提交的新事件，再持续发送。
3. 网络断开时客户端保留最后确认序号，重连后补读。
4. 同一逻辑消息的增量按 attemptNo 归属；新尝试不会拼接到旧的半段文本后面。

数据库通知允许丢失，客户端仍能从事件表查到最终状态。SSE 心跳不写业务事件。用户关闭页面不触发任务取消。

### Telegram

#### 配置与配对

1. 只有拥有者可通过同源 API 配置 Token、选择 Agent、生成口令和解除配对。Token 与配对码分别加密保存；通用 settings 写接口不能改 Telegram 内部配置。
2. 12 位无歧义随机口令 10 分钟有效，通过私聊 `/pair CODE` 一次消费，绑定 Telegram 用户及私聊 ID；群聊、机器人身份、其他发送人不创建任务或获取任务信息。
3. Token 更换、重新配对或解除配对会轮换 generation，旧按钮、旧待处理更新和旧通知失去权限。配对前排队的旧消息不能作为新任务。
4. 一个已取得数据库租约的 worker 执行 polling。先验证 bot 身份和 webhook；已有 webhook 只报告冲突，不擅自删除。渠道网络错误单独可见，控制循环继续运行。

#### 收件、任务与游标

1. 接收 update 后，先保存 generation+update_id 和经过身份检查的命令。任务命令冻结完整输入，包括 Agent、thread、目标、拥有者当时允许的交接名单与稳定来源键。
2. 在第二个事务锁定连接行，复核当前 generation 和身份，再调用已有 submitTask/respondToRequest/requestCancellation。连接锁使受理和配对撤销具有明确先后。
3. Task 与 DBOS 入队沿用自己的原子事务；如果它已提交而收件回执尚未提交，重放使用冻结的原参数与请求键，取得原任务。
4. 保存处理回执、回复 outbox 和游标后提交。下一次 getUpdates 才使用新 offset，不能提前确认尚未处理的更新。
5. 文字追问复用该渠道 thread；`/new` 新对话，`/use ID` 切换 Agent，`/stop` 走实际取消入口。执行/等待中的对话仍按原互斥规则拒绝并发追问。

#### 人工请求与通知

1. 新配对之后的完成、失败、取消和待处理请求产生通知，不批量补发历史已完成任务。相同任务状态/请求版本使用唯一通知键，状态未变时不催促。
2. 问题通知可以原生回复；回复使用已发送通知的 message_id 取得当前请求。按钮带随机 outbox ID，服务端再核对配对代、私聊、bot 消息、按钮动作和请求 payloadVersion。
3. 同意/拒绝、继续/完成/取消、交还等沿用现有决定 API；预算追加参数在网页填写。桌面控制和文件下载使用认证网页，通知不携带桌面长期密钥。
4. 回调决定重放复用原请求决定；旧版本、不同答复和已终止任务返回明确结果。旧审批不会授权下一轮工作。

#### 发送与结果未知

1. 消息入库为 pending，派发前提交 sending 意图和尝试次数，收到有效回执后保存 message_id 并标为 sent。
2. 网络断开、回执不合法或 worker 在 sending 时退出，登记 unknown。即使服务端已经收到消息，恢复也不盲目重发。
3. 拥有者在设置页核对后，显式承认可能重复的风险，才把 unknown/failed 重新入队。未知尝试计数保留。
4. Telegram 明确返回 429 拒绝时，按 retry_after 延迟重试。其他明确拒绝显示 failed；不会吞掉格式错误或不断发送同一消息。
5. Bot token 出现在 API URL 中，因此网络异常不携带原始 fetch 错误/原因链；服务返回的描述也脱敏。Secret 不进入 Task、DBOS 步骤或 outbox。
6. 解除配对阻止后续旧代派发，已经发出的网络请求仍可能到达；系统不承诺撤回外部消息。

**证据**：T09 / telegram.json 的 8 组检查覆盖受理后精确退出、问题等待重启与多轮、实际取消、回调版本、发送未知/429、撤销和手机设置页。服务端 Telegram/模型响应受控；真实 Telegram 网络、公网链接、附件及更多联动分支分别验收。

## F10 定时、时区与漏跑

1. 用户保存上游的五种计划（每天、工作日、每周、间隔小时、一次性）、执行 Agent、IANA 时区、漏跑策略、日期规则、完成条件和单次预算。首版不接受 squad 计划。
2. 只有持租约的 worker 登记一个 DBOS 计划 personal-agent-routines，每 30 秒唤醒串行调度队列；启动立即唤醒一次。Web 不启动定时器。DBOS 的 automaticBackfill 关闭，业务计划按自身游标处理漏跑，避免把停机期间每次心跳都补出来。
3. 调度事务锁定到期计划，计算本次应受理的时刻。把运行记录、冻结参数和下一次游标一起提交。来源键为例程 ID + 计划版本 + 预定 UTC 时刻。
4. 每次调度最多处理 50 个计划和 50 条待提交运行；后续调度继续处理。提交使用既有 F02，任务与队列依然同事务。提交成功但运行记录尚未保存 taskId 时崩溃，恢复用冻结参数和原键取得同一个任务。
5. 每次运行建立独立对话，同一 Agent 的任务进入原工作站串行队列；繁忙和人工等待期间保留排队任务。一次性计划受理后停用未来触发，既有任务继续排队。
6. 编辑、启停和删除按计划版本核对；删除使用归档标记并保留运行历史。已经受理的运行沿用原 prompt、Agent、时区、日期、完成条件和预算。Agent 模型、记忆在 F02 受理任务时按当时配置冻结。
7. 默认 latest 仅补最近一次，较旧的触发合并记录为可见的跳过区间。显式 skip 策略把延迟超过 60 秒的触发登记为跳过；正常调度精度允许约 30 秒及队列延迟。首版不逐条补全部历史。
8. PostgreSQL 负责当地时间转换：夏令时缺失时间向后顺延，回拨的重复时间取变更后的一次。间隔小时沿用首次激活时的绝对时刻锚点；时区变化不改变“每隔 N 小时”的时长语义。
9. “上一完整自然周”按计划时区及预定时刻计算，周一开始、周日结束；同时保存 UTC 左闭右开区间。CSV 合同配置 dateColumn 时，写入同一组日期边界。恢复与重试都沿用快照。
10. 手动运行以浏览器保存的 UUID 去重，受理时核对计划版本；确认失败的请求保留原键供重试。例程页提供历史、状态刷新与原任务链接。

**具体例子**：纽约 2026-11-02 09:00 的周报固定为 2026-10-26 至 2026-11-01；对应 UTC 区间为 10 月 26 日 04:00 到 11 月 2 日 05:00，共 169 小时。恢复到下一周时仍处理原区间。

**验收**：T11 / runtime-routines.json，检查台北、纽约夏令时、重复扫描、计划编辑、明确断点恢复、一次性忙时排队和实际网页。条件通知的受控报表链路另见 F08 / runtime-reports.json；真实模型规划、真实源网站和历史 上游项目 数据导入分别验收。

## F12 备份、升级和恢复

### 一致备份

1. 停止 Compose 入口、Web、worker 和一次性写入进程；正常关闭浏览器刷新 profile，停止本安装 guest/viewer。PostgreSQL 保持运行供导出。
2. `snapshot.mjs backup` 核对零应用写入、数据库无其他客户端、工作站 home 完整和镜像/迁移匹配，拒绝覆盖已有输出。
3. format-2 数据包包含业务/认证/Drizzle/DBOS 全库、宿主成果、所有安装 home/profile 与固定 Web/worker/guest/PG/Caddy 镜像。
4. 原配置/主密钥/安装标识另存权限 600 的独立文件；数据目录 700、文件 600。数据包含 Cookie 和文件，需使用拥有者控制的加密存储。
5. 所有文件完成后写入带认证回执的清单；离线 verify 读取完整文件，拒绝缺失/损坏/替换、符号链接及越界路径。认证不加密数据，也不替代实际恢复。
6. 工具不自动重启应用。备份之后的外部效果不会随数据库回退，恢复前按服务商记录核对。

### 升级

首版排空当前版本的执行段再升级。等待用户的任务应明确处理或取消后再排空，不能假装已经安全结束。先备份，再运行迁移和新镜像。恢复原版本时使用对应数据库与镜像备份，不假定任意数据库迁移可以反向执行。

### 恢复

1. 原安装保持离线，在无本安装容器/命名卷的同架构 Linux 目标执行 restore；先完整认证，再导入包内固定镜像、单事务恢复全库并还原文件。不清空已有安装。
2. 一个恢复事务删除网页会话/桌面票据、递增控制 epoch/清除 bootId、暂停例程/推进版本、撤销 Telegram 配对代；保存恢复事件，保留未知请求和动作。
3. 成功后只有 PostgreSQL 运行，新配置固定原身份/秘密和实际镜像，旁边保存私有恢复回执。证书重新生成，目标入口/网络规则需重新核对。
4. 拥有者检查原成果、home、记忆、凭据可用性和备份之后的外部记录，再显式启用 Web/worker/入口。重新登录、配对 Telegram，逐条核对并启用例程。未知计费和提交继续原复核流程。

**受控证据（设计稿 1.14）**：两台独立 Linux ARM VM 恢复了 9 个数据文件、6 个 home、5 个镜像；旧控制和会话被拒，两个未知任务没有新请求/动作；新任务使用恢复的受控登录 Cookie。Cookie 预置、grant 样本与延长票据均在报告单列；未重验完整凭据填写。操作、失败处理与限制见工程 deploy/BACKUP.md，报告 restore.json。普通公网 DNS、实际 VPS/ACME、跨架构和整体对照另验。

## F13 多轮对话、草稿与追问恢复

**示例输入**：第一轮“生成本周 CSV”，第二轮“把刚才报表的金额翻倍”，第三轮回答 Agent 提出的“使用哪种语言汇总”。

1. 新对话调用 F02，保存 thread 与第一轮 Task。侧栏显示对话，页面地址保留当前任务 ID。
2. 完成后在“继续对话”提交新目标。新任务可以有自己的完成条件，不自动继承上一轮的 CSV 检查或审批。
3. 受理事务锁定 thread，检查拥有者、Agent 和已有活跃轮次。已有任务仍执行/等待时返回冲突；重复请求键返回原任务。
4. 为新任务分配唯一 thread_turn，保存用户消息、近期历史快照与队列。竞争失败的事务整体回滚，不留下空消息或幽灵任务。
5. 快照读取最近最多 50 轮，按完整问答对限制为 64,000 字符，记录省略数量。保留原目标、回复/终止状态、已解决人工问答、已记录成果路径；旧工具调用和观察引用不进入新现场。
6. 模型重新读取工作站文件或观察网页再执行。修改 guest 文件时，已经提取的旧成果保持独立字节和下载 ID。
7. Agent 提问后按 F05 等待；worker 重启复用该轮历史快照和已保存模型决定。人工答复继续当前 Task，后续追问也能看到该答复。
8. 对话记录按 thread_turn 分页，拥有者可以加载旧轮次、重命名和导出。取消轮次显示真实终止状态，不能伪装成成功回答。
9. 输入草稿和待确认提交键保存在当前浏览器标签会话中。网络失败保留文字；服务器已提交但响应丢失时，刷新后使用原键重试。
10. 成功受理后清空原草稿；浏览器存储出错明确提示。无法持久保存请求键时停止发送，避免静默降低重载去重能力。
11. 新消息自动跟随到底部，用户向上阅读时保持阅读位置；提供回到最新消息的按钮。
12. 模型 Markdown 禁止执行原始 HTML，不自动请求远程图片；链接需要用户主动使用。完整任务控制和私有成果授权仍由原 API 执行。

**验收**：T17。受控检查已覆盖 23 个实际轮次（22 完成、1 取消）、竞争提交、文件修正、等待重启、取消后继续及分页；网页已覆盖受理响应丢失→刷新→原任务复用、重命名/导出、手机布局及最新回复可见。真实模型判断单独验收。

**当前边界**：侧栏列最近 50 个对话；旧任务可通过保存的任务地址进入。历史截图和所有工具原始输出没有全部拼成聊天气泡；当前显示工作站动作摘要，具体控制请求与事件继续在任务详情查看。语音输入和完整对话删除/管理继续迁移。

## F14 凭据提供、单次授权与填写

**状态**：S1—S4、S5-A身份和S5-B支付准备已有受控证据；S5-C付款提交/结果与真实服务另验。完整字段、接口边界和断点矩阵见[凭据与授权设计](凭据与授权设计.md)。

**例子**：“登录销售后台”，浏览器已有两个可编辑字段，Agent 只知道账号条目 ID。

1. Agent 观察当前登录页，保存页面/字段引用，发起 request_secret 或 vault_fill。
2. 需要新秘密时，用户从认证网页安全表单提供；专用 API 加密保存条目，将引用回复与 DBOS 唤醒同事务提交。Telegram 只指向网页。
3. worker 检查条目范围、版本、过期、精确 origin、当前控制和 DOM 目标，创建一次填写审批。
4. 卡片展示站点、脱敏条目、字段、用途、有效期和 guest 信任边界。用户可批准、拒绝或接管。
5. 批准后再次核对相同 Task/动作/页面/观察/epoch/boot。任何绑定变化均需重新观察与授权。
6. 保存派发意图及一次性消费状态，边界内临时解密，经现有 stdin 送往敏感 guest 入口。宿主/guest 日志和 DBOS 只保存非秘密元数据。
7. 批量填写后作废观察，返回字段级非秘密回执。是否登录成功由后续页面核对；是否提交或支付要有各自授权和结果。
8. 重启复用已保存回执。已派发但结果未知、部分填写或现场失效时停止自动重发，转复核或新授权；验证码不自动解锁重用。

**验收**：T18。检查安全表单事务、密文绑定、错站拒绝、过期/版本、实际批量填写、一次性条目、指定中断和意外明文持久化。S1/S2 见 runtime-vault.json，S3/S4 的guest2基线见 runtime-vaultfill-0.8.0.json；guest4原13任务与S5-B支付15、额外期限1任务见第15节及工程证据。S5-C、真实模型判断和任意网站能力继续验收。
