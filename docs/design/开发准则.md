## 1. 产品与实现边界

1. 面向单拥有者自托管，优先支持 Linux 云主机。浏览器客户端可来自不同桌面和手机系统。
2. Agent 的命令、浏览器和桌面操作发生在专属容器中；控制进程不提供任意宿主机命令接口。
3. Web 管理用户会话与提交，worker 管理执行。关闭页面不取消任务。
4. 先实现一个 worker 和单工作站串行规则；其他工作站按容量限制运行。
5. 仅新增实现当前任务所需的数据、接口和依赖。
6. 首版保留对话、模型配置、桌面、Shell、文件、记忆、例程、Telegram、费用和接管。顺序 Agent 交接适配新任务流程；并行团队后置。

## 2. 复用优先级

按以下顺序处理每个功能：检查上游已有实现 → 检查本项目已迁入代码 → 使用标准库/已有依赖 → 编写最小新增逻辑。

迁入时应记录：来源仓库、固定提交、原文件路径、修改内容、修改原因、验证方式。保留原作者和第三方许可证要求。未统计前不使用“复用了百分之多少代码”的表述。

优先保持组件 props、工具名称、消息 parts 格式、Agent ID 和已有配置含义。因存储与执行边界改变需要适配时，修改该边界及其调用链。避免并存新旧两套可写运行时。

数据库访问同步改异步必须沿调用链完成。禁止以同步阻塞包装异步数据库、吞掉 Promise 或静默返回空集合来维持旧接口。

## 3. 已选择的技术与职责

| 技术                 | 负责                                | 本项目仍需负责                     |
| -------------------- | ----------------------------------- | ---------------------------------- |
| AI SDK               | 模型请求、消息与工具 schema、流输出 | 步骤边界、预算、能力适配、业务目标 |
| DBOS                 | 执行记录、队列、等待消息、运行恢复  | 外部效果核对、工作站控制、完成条件 |
| PostgreSQL / Drizzle | 数据与事务、实体查询                | 数据含义、约束、迁移和备份         |
| Playwright           | 同一浏览器的结构化操作              | 页面身份、观察有效性、接管规则     |
| Docker / 桌面工具    | 环境和基础动作                      | 生命周期、资源限制、控制权与回执   |
| Better Auth          | 拥有者会话与认证                    | 资源授权、初始化、桌面访问范围     |

保持一个仓库、一个 npm 工程。Web 和 worker 是独立进程，可以共用构建镜像。Docker 工作站使用自己的镜像。新增 SDK 按验证版本锁定；不要在迁移时顺带升级全部依赖。

## 4. 必须保持的执行约束

- 用户任务有独立 ID，聊天只是交办与沟通入口。
- 任务提交与执行段入队必须具有明确的原子性。
- DBOS 记录是执行恢复依据；业务表保存目标、动作证据和交付状态，不另建通用恢复引擎。
- 每次模型决定和工具动作都有独立边界；不得把完整多步 Agent 循环作为一个不可观察的大步骤。
- 模型生成的工具参数、网页返回、文件内容、模型响应和网络调用均属于边界输入，需要相应校验。
- 已完成动作的重新读取不产生第二次外部效果；尚未确定的动作先核对。
- 任意 Shell 默认归为有潜在副作用的动作，不能仅凭命令外观判断它可安全重试。
- 取消后先禁止新动作，再确认在途进程和输入停止，之后才把工作站交给其他任务。
- 人工接管与自动操作互斥；交还后重新取得观察，旧页面引用和坐标作废。
- 完成状态必须对应已保存的完成条件与验证记录。

## 5. 代码与错误处理

只做当前问题的根因修改。信任内部类型、数据库约束与框架已经提供的保证；系统边界明确失败，不用泛化回退隐藏问题。

错误至少区分：配置缺失、输入无效、临时网络失败、已执行但结果未知、用户拒绝、预算耗尽、验证不通过。工具返回结构应表达实际状态；不能把“没有报异常”统一映射为业务成功。

针对单次用途直接使用清晰函数，不创建通用工厂、策略类或插件层。只有出现第二个真实实现且共享边界已明确时，才考虑抽象。

禁止为空想的极端情况增加兼容分支。对已经存在的外部断连、进程残留、重复消息和登录失效，按本文档规定处理。

沿用用户对检查工具、摘要算法及提交署名的限制；具体上层约束见 仓库根目录的 `AGENTS.md`。

## 6. 任务与资源互斥

DBOS 的分区队列负责工作站任务调度，工作站控制记录负责人工/自动控制权和旧命令失效。二者解决不同问题。

首版只有一个 worker，不实现通用分布式锁服务。服务恢复必须先对仍在运行的容器进程和控制连接进行核对，再让恢复的任务发动作。无法确认旧动作已停时，工作站保持隔离状态；必要时停止该工作站以结束残留进程。

不能用“排队数量为一”推导“没有遗留 Shell 进程”。后台程序确实可能比原任务活得久，这一点应纳入验收。

## 7. 凭据、访问和数据

初次拥有者通过部署端命令和单数据库事务创建账号，公开注册始终关闭。单人部署仍然要对每个 API、server action、成果和桌面资源做会话检查。

Web 不持有 Docker socket。Agent 容器不挂载宿主目录、数据库连接信息、部署主密钥或模型 API key。worker 是受信任的控制进程，访问它等同于访问高权限控制面。

密钥只在必要的调用边界取用，不写入工作流参数、步骤返回值、消息、截图注释或日志。页面和浏览器 profile 可能包含登录信息；文件和截图按私有数据交付与清理。

网站凭据按 F14/T18：安全表单独立提交、密文与引用回复同事务、精确 origin 和动作级授权、瞬时传值、一次性消费及未知结果复核。通用 action 参数会保存，敏感值不能直接作为普通填表参数。拥有通用 guest Shell 时，秘密进入 guest 后可被站点和 guest 代码接触，产品说明必须包含这一边界。

不要宣称具备任意 Shell 时，所有可能的发送、删除或外部请求都能被审批卡片完全覆盖。首版明确支持的审批动作必须在执行入口核对目标和参数版本。

## 8. 文档和事实表达

使用“已核查源码”“文档支持”“设计决定”“实验通过”区分证据等级。源码中存在函数，只能证明该实现存在；实际成功率和端到端性能需要实验。

分别记录源码应用协议、实际运行版本、已应用数据库迁移、工作站协议/镜像与最后验收版本。测试命令存在也需要核对实际执行分支、案例数量及证据对象；仅通用检查通过不能证明新增功能通过。规划升级不得写成已经应用的迁移。

不把代码行数、框架数量、开发语言或未经测量的速度倍数当作先进性的证据。报告实际完成率、介入次数、已知费用、耗时和恢复结果。

对复杂机制给具体例子，例如“第二份报表下载后断电”或“用户接管时旧输入仍在运行”。出现新事实导致计划失效时，更新相关决策和验收项，不悄悄改变承诺。

## 9. 验证与完成定义

每个非平凡变更提供一个最小有效验证。先用固定模型响应、可控网页和样例文件，再做必要的真实服务联调。

日常验证只覆盖本次变更及受影响调用链；阶段结束进行对应集成验证；发布候选执行完整验收。已通过的全量检查仅在相关变更、失败或未解决疑问出现时重跑。

一个工作项完成需要：可检查的变更、对应验证通过、错误路径说明、文档同步、来源登记。测试未执行时写明未执行，不使用“应该没问题”代替记录。

“达到参考项目保留范围”“真实任务能完成”“指定场景优于参考项目”和“可自托管发布”分开验收。按实施与验收第 9 节固定基线、模型、账号、初始现场及预算后比较，保留失败和人工介入记录。

## 10. 阶段推进和沟通

按《实施与验收》的依赖顺序推进。遇到已授权范围内的普通实现选择，按现有决策继续；产品范围变化、真实账号凭据缺失或对外发布等需要用户参与的事项集中说明。

每轮汇报包含：完成的功能、复用了哪些模块、验证结果、剩余阻碍和下一项。避免把读取代码、准备环境或整理文件表述成产品功能已完成。

## 已核实的实现约束补充

- 任意 Shell 所在的系统层可被 Agent 修改；只读观看必须位于独立受控边界。
- 隔离模式只是数据库标签；必须停止实际进程后才能登记隔离完成。
- 冷边界重建保留 home/profile，丢弃系统层和内存态现场；界面和文档明确告知。
- UI 验收需要实际画面内容；连接握手、模型文字或完成提示均不能单独代替成果证据。
- 新改动优先运行相应的定向检查，保留早期失败记录，避免反复全量测试。
- 已保存的模型回答优先复用；未得到回执的请求可能已计费，先取得再次请求的明确授权。
- 记忆修改与其业务回执同事务，重放旧写入不会复活后续已经忘记的笔记。
- 长期记忆会进入所选模型上下文，按数据库笔记管理，不存放密码、API key 或验证码。
- 对话受理锁定 thread 并分配轮次；历史在受理时冻结，原问答与人工答复保留，旧审批和桌面引用不赋予新动作权限。
- 受理响应丢失时跨重载复用原请求键；成功受理才清空草稿，存储失败必须可见。

- Telegram 只在持有数据库租约的 worker 运行；先保存冻结命令，处理完再推进游标，恢复沿用来源键。
- 外部通知先保存派发意图；未知结果经用户承认重复风险后重发，只有明确拒绝的 429 自动按时延重试。配对撤销轮换 generation，旧通知和按钮不能获得新权限。

- 每次实际模型请求独立记账，成功重放不新建请求；旧费用和价格快照不随配置更新而重写。
- 月预算与模型调用准入使用同一短事务锁；预算开启时串行付费请求，未知计费不静默视为 0。人工核对单独保存并记录审计事件。

## 11. 流程编译增量准则（1.25）

1. 复用 Task/DBOS/runtime/model/actions/控制与成果链，只增加下一步选择和流程状态。
2. 源轨迹按外部输入清理秘密并校验；候选在独立输入上验证，完成合同固定。
3. 新 Task 重新执行并记账，同 Task 中断恢复才复用已知回执。
4. 运行时重取控件与观察，旧授权、ref、epoch 和坐标不跨次作为执行凭据。
5. 首版有限结构计划、本地显式选用，先做一项原生应用；未支持情形明确报错。
6. 修复前核对已发生效果；未知发送、填写、Shell 和模型费用沿原复核规则处理。
7. 编译/检查/失败/修复/人工成本完整登记，首次探索去重，GUI 与混合执行分别对照。
8. 每阶段只做相关验证，新增阶段通过前标记待实现/待验收；实际检查命令随实现提供。
