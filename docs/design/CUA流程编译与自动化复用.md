## 1. 目标与可验证承诺

技术方向：将实际完成且检查通过的任务轨迹，编译成参数化、可检查、可修订的自动化流程。重复任务优先执行已验证流程，遇到明确失效的步骤时调用模型处理局部问题。

候选产品表达：“第一次探索，后续复用；重复电脑任务，越跑越省。”速度、费用和可靠性分别测量；通过对照后再发布具体结果。

本阶段沿用单拥有者、单 worker、独立 Linux Docker 工作站；CLI、DOM 和 GUI 共用原工作现场。多 Agent、伴侣形象、聊天渠道扩张、完整虚拟机后端和插件市场继续按原范围安排。流程包为后续社区扩展提供格式，首版交付本地流程保存和显式运行。

关键区分：

| 对象                   | 作用                         | 新任务如何使用                                               |
| ---------------------- | ---------------------------- | ------------------------------------------------------------ |
| 同一个 Task 的动作回执 | 恢复中断，核对已经发生的动作 | 同 Task 复用已确认结果                                       |
| 已编译流程             | 保存可参数化的执行方法       | 创建新 Task，重新执行真实动作并产生新回执                    |
| 普通 Skill             | 承载知识、说明和脚本         | 可作为编译器输入或流程附属说明；本增量在自动提炼、验证与修订 |
| Routines               | 决定何时提交任务             | 未来可引用固定流程版本，沿用原触发入口                       |

一次成功演示只证明该实例成功。编译产物先成为候选，经过参数变化和独立检查后才标记可复用。

## 4. 第一版范围

首条纵向链路：

1. 执行一个无真实账号、无外部发送的本地桌面任务。
2. 宿主固定检查器确认结果。
3. 用户点击“保存为流程”，指定参数和检查条件。
4. 编译器从该 Task 的可用轨迹生成候选。
5. 在独立样例上换参数试跑，记录成功和失败。
6. 通过后按固定版本运行；失败时显示停止点和证据。
7. C3 再加入有界局部修订。

第一批操作计划采用固定结构 JSON，复用现有 TypeScript/Zod。宿主解释有限操作集合，每个实际动作仍通过 executeAction。模型生成的任意 JS/Python、命令字符串不在宿主求值。

首版由用户显式选定流程版本和输入。自动检索、自动判断重复意图、向量索引、任意代码发布和市场分发留待真实需求。

## 5. F15：从成功轨迹编译流程

### 5.1 受理与输入

源 Task 必须属于当前拥有者，已经结束，并且检查等级符合该任务验收合同。用户确认输入变量、允许的应用/路径/站点和固定结果检查条件。

创建一个新的编译 Task，冻结 sourceTaskId、源执行段、源动作序列和用户参数声明。继续通过原提交/队列/预算入口受理。源 Task 和编译 Task 的操作、计费和状态分别保存，并以 sourceTaskId 关联。

编译仅读取 allowlist 中的动作元数据、参数模板、成功结果摘要、必要观察和检查证据。清理秘密、验证码、剪贴板隐私、会话 Cookie、控制票据与保险箱解密内容。源参数中敏感字段难以分离时，将相应步骤设为人工检查点或拒绝编译该段。

历史截图作为可选私有证据，仅在本次编译确有需要时送给已选模型。流程包保存证据引用；导出包使用经过审查的样例。

### 5.2 提炼规则

- 常量：应用名称、已确认控件含义、固定业务字段。
- 参数：文件路径、目录名称、日期范围、输出名、明确声明的业务输入。
- 输入验证发生在包加载、用户参数、模型候选、网络或 guest 结果等边界。
- 单条轨迹提炼出的参数是待验证假设，通过新输入测试后才作为支持范围。
- 从轨迹中删除无效尝试和临时找路步骤，保留被验证必需的观察、等待与操作。
- 旧 browser pageId/ref/observationId、坐标、epoch 和 bootId 都作为历史证据，运行时重新解析。
- 人工键鼠动作当前没有完整语义轨迹。包含人工接管的片段先保留 human_checkpoint；当前输入不足以自动学习人工示范。
- 源任务依靠 Shell 完成的部分标记 CLI；后续评测保留相同通道约束，单独报告原生 GUI 与混合执行。

### 5.3 候选输出和信任边界

候选包含参数 schema、环境要求、有序步骤、前置条件、后置条件、完成检查和证据引用。结构校验通过后进入 verifying，使用独立样例重新执行。

检查合同来自拥有者确认或版本化的固定任务检查器。编译模型可以提出检查建议，候选不得削弱合同、重写宿主检查器或把自身摘要作为通过条件。

这是 IR 示意。args 是编译层参数：当前 browser_download 没有 outputName 入参；执行适配器按已验证的下载路径规则绑定结果，需重命名时通过单独、可记账的 guest 动作完成。包字段须由实际 schema 定义，禁止将示意直接透传给现有工具。

首版仅需有序序列，操作集合：

| 操作             | 职责                                                     |
| ---------------- | -------------------------------------------------------- |
| observe          | 读取当前页面、窗口或截图，生成本次控制代观察             |
| action           | 解析当前目标后调用已有工具；一条副作用对应可恢复动作记录 |
| assert           | 运行固定状态检查，标明 guest 状态证据或宿主成果证据等级  |
| human_checkpoint | 复用原人工请求、接管和交还机制                           |

步骤 ID 在同一版本内固定；跨次运行使用各自 Task/action 身份。参数采用结构化绑定，文件名不插入可执行命令模板。需要 Shell 的已确认流程只在 guest 执行，复用现有日志、权限和未知效果规则。

原生 target 只定义所选应用确实能提供的字段，例如可访问控件 role/name 或窗口状态配合稳定键盘导航。AT-SPI、OCR 和视觉定位保持按任务选择，首版不新增通用多后端框架。某种定位能力尚不存在时，先实现所需最小适配并注明支持边界。

## 7. F16：在新 Task 中执行已验证流程

1. 用户选择 ready 版本和参数；服务端核对拥有者和支持范围。
2. 受理事务固定版本、参数、完成合同和预算，创建新 Task/流程运行记录并入队。
3. worker 按原方式取得工作站、处理取消、人工控制和容量。
4. 检查镜像实际 ID、协议、相关应用、语言和必要登录/文件条件。
5. 读取当前观察；唯一匹配目标时解析成本次真实 pageId/ref 或桌面坐标。
6. 保存动作意图，经 executeAction 派发，取得实际回执。
7. 检查后置条件，写入步骤检查点；进入下一步或进入明确失效分支。
8. 在宿主提取成果并调用固定检查器，通过后沿用原 complete_task/交付路径。

所有“流程下一步”和“模型下一步”在同一个 worker/runtime 和 Task/DBOS 链内选择。只增加确定下一步的方法，动作派发、控制和恢复继续由同一入口承担。

单个零模型流程仍有最大动作数、总时限、检查等待和修复次数上限。现有 maxSteps 主要限制模型决定次数；实施时需要补齐确定性流程的动作/时间上限，避免零模型路径绕过任务预算。

初期每个可见副作用后检查结果。检查可以使用廉价 guest 状态读取，无需每步调用视觉模型。等待使用具体条件和期限，超时以真实状态进入失效/未知复核。

显式选择的流程若前置条件不满足，展示原因，并提供“按普通 Agent 任务处理”。已执行部分需先核对，继续路径保留已知副作用；输入不适用时不得静默从头开始。

## 8. F17：失效、人工介入和有界局部修订

| 状态                                 | 行为                                                 |
| ------------------------------------ | ---------------------------------------------------- |
| 目标不存在/出现多个候选，且尚未派发  | 保留检查点，读取新现场，允许局部修订                 |
| 旧观察/控制版本失效                  | 停止当前决定，等待控制归还并重新观察                 |
| 动作已执行但后置条件失败             | 先核对真实效果，再确定后续步骤                       |
| 派发后断连、Shell 中断或外部效果未知 | 复用 needs_review；先核对结果，再决定继续            |
| 登录/验证码或人工选择                | human_checkpoint；交还后验证当前步骤是否已经由人完成 |
| 完成检查失败                         | 任务尚未交付；展示证据并在原合同下纠正               |

C3 首版每个运行最多一次模型局部修订。模型只得到失效片段、当前观察、已发生效果和冻结完成合同。模型可以生成该片段的新候选；固定解释器校验操作范围后，在剩余预算内执行并验证。

可见状态发生变化时，从步骤前置条件和已知后置条件重新选定恢复位置。用户手动完成某一步后，先确认该结果，避免再次执行。

修订不修改正在运行的包版本。运行内保存 repairVariant 和实际动作；完成后生成下一版本草稿，在独立样例验证通过后才可启用。已有 ready 版本和历史失败保持原记录。

本设计解决可检查局部变化。目标大范围改变、环境未知或效果无法核对时，任务通过明确原因转人工或结束，不承诺任意界面自动修复。

## 9. 数据、原子性和模型费用

先复用 task_model_decisions/attempts、task_actions/attempts、task_requests、artifacts 和事件表。

最小新增候选：

- workflow_versions：稳定 workflowId、revision、ownerId、状态、plan、参数 schema、环境要求、固定检查器 ID、sourceTaskId 和验证证据引用。
- task_workflow_runs：一个 Task 对应固定流程版本、运行阶段、参数快照、当前步骤、检查点及局部修订引用。

编译和修复模型请求继续保存到原 Task 模型账本；步骤与旧动作的映射可以放入流程运行记录及既有事件，不为首版再建平行动作日志。C1 出现明确查询或原子性需求后，才增加字段或表。

状态：

```text
draft → verifying → ready → retired
           ↓
        rejected

Task 保持现有 running / waiting_user / completed / failed / cancelled 等状态
流程运行记录在同一 Task 内描述 executing / repair 等内部阶段
```

ready 版本内容固定；再次验证失败留在候选。停用和删除由拥有者执行，存量 Task 使用已冻结版本完成或由拥有者取消。

流程推进和已确认动作/检查点提交沿用既有事务边界；Task 接收和 DBOS 入队保持同事务。逻辑动作身份由 taskId、segmentNo 和动作序号产生；恢复时从持久映射取得相同身份。流程修订分配新动作身份，已知成功动作不重新派发。

普通 Agent、编译、验证、执行、修复分别标记 phase/workflowId。修复模型沿用原 provider、价格快照、月预算和未知请求复核。未知费用保持未知，不进入“零成本”汇总。

## 10. 坐标、现场和隐私的前置条件

C0 首先核查主会话是否已经修改相关模块，以当前代码为准：

1. 截图实际尺寸、显示尺寸、缩放和裁剪偏移进入同一坐标契约；按 provider 已知约定转换，禁止根据数值大小猜测体系。
2. 首次对齐测试用于验证明确映射，保留未参与拟合的测试点；非规律误差进入定位问题分析。
3. 桌面操作绑定当次 observationId、控制 epoch 和 boot；某一观察只授权规定范围的动作，屏幕变动后重新观察。
4. 模型的操作图像默认仅使用当前控制代最新一帧。需要局部图时，标记其与同一帧的映射；历史截图保留私有审计用途，避免混入当前定位依据。
5. 用户接管后停止在途操作；交还后重新观察、检查当前步骤，按原控制协议恢复。

这些是待实现的强化项；既有 epoch 和手动接管已有证据，逐帧绑定与最新图像策略须单独验证。它们保证“依据哪一帧”可检查，无法消除屏幕异步变化或模型认错按钮；执行前仍检查相应状态。

流程和轨迹包含隐私内容，默认 owner 私有。流程导出剥离秘密、真实联系人、生产文件和登录状态。第三方流程按外部输入校验；静态计划在宿主由固定代码解释，任意脚本只允许在受限 guest 路径执行。

首批样例使用本地无害数据。通用 Shell、键鼠和浏览器尚无完整语义级强制审批；本次学习流程不扩大该保证。后续对外发送、删除重要文件、付款等流程必须接入相应精确确认与未知结果核对。

## 11. 编译经济性和评测设计

定义同一任务族、同一通道约束、相同模型、环境、样例输入和完成合同的普通执行成本 B(i)。

实际流程成本包括：

```text
F = 首次探索 + 所有编译尝试 + 参数提炼 + 候选验证 + 专属环境准备
W(i) = 第 i 次执行 + 状态检查 + 局部修复 + 人工接管 + 结果核对
累计净节省 = sum(B(i)) - (F + sum(W(i)))
```

比较相同 N 次实际用户任务时：若第一次探索本身交付了第一个用户结果，它只计作第一个任务成本一次；B(1) 与该探索对应，后续 W 从第二个任务计起。验证用例、失败候选和重试是额外开销，全量计入 F。数据表同时保留原始 phase，汇总避免重复相加。

费用、耗时、模型调用、人工时间分别统计，避免把不同量纲相加。模型定价缺失时仍报告请求/token/时长及未知金额；无法推算费用回本次数。普通执行波动采用匹配输入和多次运行记录，保留中位数、范围及原始样本。

首版用户显式编译，编译和修复有预算上限；有复用计数和实测收益后再决定自动编译策略。先使用简单收益阈值，PACE 的学习型策略暂不引入。
