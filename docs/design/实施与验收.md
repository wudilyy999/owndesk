## 1. 先做四个决定架构能否落地的实验

| 实验                 | 最小内容                                               | 通过条件                                                 | 不通过时的动作                                                  |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------------- | --------------------------------------------------------------- |
| G01 持久化提交与恢复 | 同库事务写任务并入队，三个固定步骤，第二步附近中断     | 同事务回滚、重复请求去重、已记录步骤复用、恢复后产物正确 | 核对 SDK/数据库版本与连接方式；修正设计，不用未验证接口继续开发 |
| G02 浏览器共用现场   | 同一 profile，由人工登录、DOM 读取、截图和桌面操作交替 | 登录、页面和下载文件共用；浏览器重启后行为明确           | 验证原 Chromium 与 Playwright 兼容；必要时调整浏览器构建并记录  |
| G03 服务端控制权     | 只读观看、控制接管、旧连接撤销、残留输入模拟           | 前端改 viewOnly 不能绕过只读；Agent 确认停止后才开放输入 | 先修控制和进程回收，不开放公网接管                              |
| G04 外部效果恢复     | 动作成功与回执之间强制中断，覆盖下载和不可确认提交     | 可核对动作不重复；未知效果明确等待复核                   | 调整回执与验收策略，缩小自动恢复承诺                            |

G01/G02 可以使用独立的极小实验程序。G03/G04 在最小工具执行器具备后完成。它们只验证实际边界，不为实验创建通用框架。

自托管是核心需求，应在剩余界面与记忆增强之前验证。P7 分两次推进，继续共用一个仓库、一个 npm 工程与现有 worker。

| 步骤               | 输入与操作                                                                         | 放行条件                                                      | 失败后修什么                            |

## 3. 工期口径与依赖

核心执行依赖为 P0 → P1 → P2 → P3 → P4；P5/P6 按具体调用链推进。P7 的私有部署与恢复演练在稳定执行、控制和认证底座上提前开展，发布候选再汇合保留功能与真实服务验收。阶段编号用于组织能力，不能把部分条目通过写成整阶段完成。公网开放始终依赖认证、控制、网络和部署门槛通过。

后续优先级为：Linux 私有部署/网络隔离与备份恢复 → 剩余保留功能与顺序交接 → 已授权真实服务联调 → 同条件对照。稳定的单项能力可提前进行真实模型联调；无需等待费用趋势或记忆增强。使用真实账号、费用和对外发布分别遵守已有授权范围，未获授权不新建其他聊天或委派子 Agent。

粗估合计 **26—42 人日**，按一位熟悉 TypeScript/全栈工程的开发者计算。比上一版 21—35 人日增加了取消清理、服务端控制权和执行段交接的明确工作。该数字属于范围估算，P0/P1 后按实际结果重估，不对应对用户个人学习或实现速度的承诺。

## 5. 断点实验具体脚本要求

使用可控网站，提供下载、可查询创建结果和“提交后暂不返回”的测试动作。能够确定业务效果发生时间，避免通过随机杀进程猜测是否覆盖窗口。

每个代表性动作覆盖：动作前中断、效果发生后回执前中断、回执保存后中断。只读动作应可重新观察；可核对写入应找到已有结果；无法核对的提交应进入 needs_review。

取消实验启动一个会持续输入或写文件的受控命令。取消后核对实际进程和输入是否停止，不能只断言数据库 status 字段。

### 9.6 结果不达标时怎么改

- 只在视觉定位中失败：检查 DOM 覆盖与观察质量，保留已验证恢复机制。
- 程序机制正确但模型选错工具：优化工具描述/上下文，单独记录模型影响，不换整个数据库或执行框架。
- 接管或授权太频繁：按介入原因做最小流程改进，保持秘密和控制边界。
- 容器重建导致现场丢失：测量影响，优先固化必要依赖或限制 Shell 范围，再决定隔离方案。
- 自托管成本高：先测空闲服务、桌面和只读 sidecar 的分别消耗；有数据后决定按需启停。
- 保留功能缺失：先补齐同一调用链，再新增产品定位外的插件、多租户或并行团队。
