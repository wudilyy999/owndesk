# 从设计到实现的决策

## D09：拥有者通过部署命令初始化

原设计 F01 允许一次性初始化凭证和网页注册。实际实现选择部署端命令：
`scripts/owner.ts` 用一个 PostgreSQL 事务创建认证用户、密码账号、单拥有者记录和实验 Agent，
用事务锁和单拥有者约束处理并发。公网的邮箱注册接口始终关闭。

理由：当前单拥有者目标可以少维护一个高权限公开接口，同时直接消除抢先初始化的窗口。
代价：第一次部署需要在部署端执行命令。它不影响日后的网页登录体验。
证据：`tests/web.ts` 已验证公开注册返回 `EMAIL_PASSWORD_SIGN_UP_DISABLED`。

## D10：DBOS 保留为 Next.js 服务端外部包

DBOS 5.3.0 的遥测组件按运行配置延迟加载。Next.js 的打包器提前扫描了这些可选模块，
导致缺少遥测依赖的构建错误。`next.config.ts` 使用 `serverExternalPackages`
让 DBOS 和 pg 由 Node 原生加载，避免为关闭的遥测能力安装额外依赖。

证据：修正前构建失败，修正后 production build 通过；独立 worker 与 G01 仍使用真实 SDK。
这项修改调整了打包边界，持久化和事务模型保持原设计。

## D11：按安装版本使用队列与事务接口

实际安装 `@dbos-inc/dbos-sdk` 5.3.0。
任务提交使用 `DBOSClient.enqueueInTransaction`，传入已经 BEGIN 的 pg PoolClient；
队列按该版本的 `partitionConcurrency: 1` 配置。`DBOS.registerQueue` 在 launch 之后执行。

已用 G01 验证并发去重、整体回滚和两个检查点后的恢复。
测试只覆盖已有步骤记录的恢复，G04 继续验证外部效果与回执之间的窗口。

## D12：由浏览器控制服务统一管理退出

工作站沿用 Debian Chromium 和原 profile 路径。Playwright 控制器以有界面模式运行，
DOM 和桌面键盘已经在同一登录现场交替完成操作。

G02 暴露了容器重启后 Cookie 丢失的问题。最小 headless profile 探针可以保存 Cookie，
说明持久化 API 本身有可运行证据。控制服务已改为独占处理信号退出，关闭 Playwright
默认的重复信号处理；同条件重测已经通过：信号处理由控制服务统一接管，Cookie 在容器重启后保留。
该版本的关闭流程需要让 `context.close()` 正常结束，不能让默认信号处理与自定义退出并行。
证据：docs/evidence/g02.json 及对应原始 browser.log、Cookie 元数据和截图。

## 测试与证据口径

`docs/evidence` 保存不含密钥的汇总；原始日志和截图保存在被忽略的 `data/experiments`。
固定模型/已知答案实验仅证明执行机制。真实模型能力、外部网站兼容性、总体可用性和成本
需要后续指定输入的对照实验，不能从当前检查点实验直接推导。

## D13：提交成功立即建立本地任务视图

API 返回任务 ID 后，界面直接加入对应任务并订阅该 ID。去掉“先受理、再依赖一次列表请求才显示”
的额外网络条件：列表请求失败不应让已受理的任务看起来提交失败。
响应丢失时保留原请求键，重试仍命中原任务；用户明确开始下一次任务时再生成新键。

## D14：界面检查必须绑定新任务 ID

视觉复核发现第一次 UI 检查可能匹配上次任务的“已完成”，而新任务还在排队。
那次结果已在原始记录中作废，并保留原因。检查现已先取得 POST 返回的 taskId，
等待该任务详情出现，再检查其完成事件和成果下载。

界面同时把详情绑定到当前选择的 ID，并按最新发起的读取更新视图，避免旧任务详情短暂残留
或较早的网络响应覆盖较新状态。最终通过的截图应同时显示对应 ID、完成事件与下载对象。

## D15：观看服务独立于可执行 Shell 的工作站

Shell 允许修改 guest 系统；将只读 VNC 与 Shell 放进相同可写系统层，前端 viewOnly 与服务器启动参数都可能被改变。
采用独立只读 sidecar，只共享 X11 socket。`-viewonly -noremote` 在服务器端丢弃输入；工作站使用单独控制入口。
代价：每个工作站增加一个轻量观看容器。G03 已用具备输入能力的原始 RFB 客户端验证。

## D16：取消和 Shell 交接使用真实容器边界

普通进程组清理覆盖不了 setsid 或守护程序。取消直接从宿主机停止并移除工作站；正常交接在使用过 Shell 时执行冷边界重建。
home/profile 保留，系统目录安装的软件与内存态网页不会保留。纯浏览器交接保持热现场。
worker 恢复先查看 PG 中的 Shell 历史，再决定是否运行原可写系统层。guest 的 shellUsed 标记仅作辅助。
G03 验证后台和活动 Shell；扩展实验验证控制器 SIGSTOP 后仍可停止边界。

## D17：控制票据一次性，交还撤销实际连接和残留输入

票据绑定会话、拥有者、工作站、模式和 epoch，30 秒过期，原子领取一次。
票据放在 WebSocket 子协议，异步上游连接完成后重新校验。交还先关闭客户端与上游，再检查 VNC TCP 与释放键盘/鼠标状态。
会话每两秒复核；G03 验证旧票据、旧连接、按住 Shift/鼠标、注销和旧模型版本拒绝。

## D18：外部效果与业务回执之间确定制造中断窗口

G04 不依赖随机等待碰运气：在实际工具执行期间外部持有任务行锁，让 worker 的回执事务阻塞；下载成功后强制结束 worker。
恢复复用终端 journal，下载计数与派发尝试都为 1。
另一个测试站点提交后不回复，再结束 worker/controller；恢复进入 needs_review，提交仍为 1。
这证明代表性进程中断窗口的处理，尚未覆盖整台宿主机断电。

## D19：不同工作站独立控制作业

工作站内生命周期仍串行；控制轮询按工作站建立单独作业，缓慢的 guest 不阻塞其他工作站的取消。
控制器 quiesce 使用短超时；失败先确认容器边界停止，再登记隔离。
无法确认停止时继续传播错误并执行安装级紧急停止，不用 quarantined 标签代替真正停止。
扩展实验已验证“一个控制器挂起接管，同时取消另一个工作站”。

## D20：跨容器观看禁用共享内存截屏

首次桌面 UI 检查通过 VNC 握手，但截图显示黑屏，该记录已作废。
两个容器共享 X11 socket，IPC 命名空间保持隔离；观看端使用 `-noshm` 读取画面，不合并 IPC 命名空间。
加入实际 framebuffer 像素检查后，桌面/390px 手机截图与接管/交还检查通过。
证据：desktop.json 与其原始截图；早期失败截图仍保留在 data/experiments。

## D21：本地 Docker 代理的实际可达性是就绪条件

Colima 在 Docker inspect 已报告映射后，宿主端口仍可能短暂拒绝连接。
工作站启动阶段等待真实 HTTP 可达，超时明确失败；在用户领取一次性票据之前完成准备。
私有 Docker 网络部署的可达性继续在容器网络中处理，不把 loopback 地址发给远程用户。

## D22：桌面界面复用单画布，连接随服务端控制版本重建

适配原 Screen 的移动画布、放大模式与 noVNC 加载方式；模式和 epoch 改变时获取新票据并重连。
前端只读开关用于交互反馈，安全边界由 D15 的服务器保证。关闭接管窗口保持任务暂停，交还由明确按钮触发。
已通过真实 Next.js、noVNC 画面、接管、交还重连、移动布局和实际取消检查。

## D23：模型生成与工具动作分步，业务回答先于框架检查点保存

AI SDK 的工具只声明 schema，不提供 execute 回调。每次 generateText 返回后，先保存
task_model_decisions 与事件，再让 DBOS 步骤返回；工具逐项进入独立步骤。
受控恢复实验精确阻塞框架检查点：业务回答已保存时结束 worker，恢复复用原回答且不重复生成。

pending 请求没有确定回答时等待 model_retry 授权；再次请求保留 uncertain_attempts。
maxRetries=0 防止 SDK 内隐式重试。调用失败与未知用量不能默认为零费用。
已保存回答绑定旧 epoch 时，工具仍拒绝旧现场并要求重新观察。

证据：runtime.json、runtime-recovery.json。实际价格目录继承上游，只作为估算。

## D24：采用实际凭据快照脱敏并适配安装版本的消息协议

先读取本次凭据，再用同一快照创建 provider 与脱敏函数，避免密钥轮换时出现请求和日志脱敏不一致。
秘密不进入工作流参数；错误、响应和发往模型的字符串过滤实际 provider key。
所选 AI SDK 7 使用 instructions；普通消息不混入 system。
同一批工具结果连续追加，再处理图片提升和人工交还说明，避免未回答工具调用之间插入 user 图片。

证据：runtime-cua.json、runtime-recovery.json、runtime-ui.json；该处理不承诺自动清除所有网页秘密。

## D25：成果在工作站外提取并检查

worker 读取有界 docker cp 归档，只接受单个普通文件，通过 tar 标准输出读字节而不解包容器路径。
单文件上限 20MB，使用稳定服务端 ID 保存。CSV 校验真实日期、范围、表头与行数；失败返回模型修正。
结构通过不证明来源真实，摘要与人工确认分别标注验证强度。

证据：artifacts.test.ts、runtime.json、runtime-ui.json。真实来源比较器按具体任务后续接入。

## D26：记忆修改与事件回执同事务

复用原 memory_write/memory_forget 与 memories 表，保留每个 Agent 的笔记范围。
PG 事务同时修改笔记和写 task_events 回执，模型步骤重放先读取原结果。
避免“先写记忆、后忘记、再重放旧写入”时复活已删除笔记，无需新增账本或向量库。

新任务加载最多最近 30 条、12,000 字符；设置页管理笔记。任务保持受理时快照，删除不抹除历史审计。
记忆随上下文发送给选定 provider，界面明确告知并禁止用于秘密保险箱。
证据：runtime-memory.json、runtime-ui.json。相关性选择与通用流程复用留待后续任务验收。

## D27：每轮任务保留独立执行边界，对话历史在受理时冻结

保留 threads/messages，一轮追问对应一个新的 Task。受理在同一事务中锁定 thread，
拒绝其他仍活跃的轮次，分配唯一 thread_turn，保存用户消息、历史快照与队列。
排序使用明确轮次，避免 PostgreSQL 事务起始时间和实际提交顺序不同造成交叉。
0006 迁移回填已有轮次；旧任务保持原应用版本，不交给新循环强制重放。

上下文读取最近最多 50 轮，按完整问答对控制在 64,000 字符，记录省略数量。
包括原目标、最终回复/终止状态、已解决的人工问答与成果路径；排除旧工具调用和桌面引用。
历史审批保留为审计事实，不授权新的外部行为。修改 guest 文件不覆盖已经提取的旧交付物。

证据：runtime-chat.json 的 23 个实际持久化轮次，覆盖竞争提交、问答等待重启、取消后继续、
分页和隔离；thread.test.ts 覆盖完整问答裁剪及导出。真实模型判断仍未评估。

## D28：草稿与未确认提交键在同一浏览器会话中保留

复用 上游项目 的 Composer 键盘/IME、草稿与 Transcript/Markdown 交互，服务器进度改走现有任务事件。
成功受理后清空草稿，网络失败保留输入；发请求前保存包含完整参数的幂等键。
服务器已提交而响应丢失时，刷新后使用原键重试，返回原任务。不同参数生成新键。
草稿属于浏览器会话数据，不是长期记忆；浏览器存储出错会明确显示，无法保存提交键时停止发送。

证据：runtime-ui.json 实际拦截并丢弃已受理响应，刷新后 HTTP 200 复用原任务，仍只有两轮和三次追问模型请求。
页面地址保留任务 ID，重载回到同一执行现场。Markdown 禁止原始 HTML 执行和远程图片自动请求，
测试中的脚本未执行、跟踪图片未访问；聊天滚动使用原有依赖，重载后确认最新回复实际可见。

## D29：Telegram 冻结命令与原任务入口共享业务去重

仅在租约 worker polling。收件先登记 generation+update_id 与冻结输入，再锁定配对状态调用现有任务/决定/取消 API，最后提交回执、通知与 cursor。Task 已提交而 inbox 未提交时，稳定来源键和原输入找回原任务。

Token 更新与配对代撤销同事务；旧代、其他私聊/群聊、过期口令不执行任务。通知按钮绑定 outbox、bot 消息、配对身份和请求版本；原生回复绑定已发送问题通知。旧请求决定没有新一轮权限。

证据：telegram.json 精确用数据库触发器/外部锁制造提交后窗口，退出再恢复只保留一个 Task/workflow；真实模型运行循环（受控回答）等待期间重启，手机回复后完成，同线程追问读取旧回答。

## D30：Telegram 发送未知结果保留，不默认重发

普通 fetch 与格式能力从上游复用。outbox 先提交 sending，收到有效回执才标 sent；断连、不合法回执或在途进程退出记 unknown，保留未知次数。用户必须在设置页承认重复风险后才可重新入队。仅明确返回 429 的拒绝按 retry_after 自动重试。

已有 webhook 报告冲突，不自动删除。Token URL 对应的 fetch 原始错误和 cause 不记录，服务描述中的 Token 也脱敏。传输故障只更新渠道状态，不停掉桌面控制。APP_URL 手机可达性与真实 Telegram 联调仍需验证。

证据：telegram.json 的已收到后断连、sending 时退出、恢复不重复、显式重试、429、Token 回显脱敏、撤销以及实际手机设置界面。通知暂用短摘要与认证网页链接，附件和更多接管/预算联动仍待迁移。

## D31：模型决定与实际请求的费用分开记录

task_model_decisions 保存恢复所需的逻辑回答，task_model_attempts 保存每次实际尝试。成功回答复用不产生新请求；未知、重试与跨月请求各自保留时间/费用。价格快照在准入时保存，之后修改价格不改旧记录。费用 bigint 加安全整数边界，避免原 integer 溢出。

旧记录缺少重试时刻，回填时保留原始时间并标 legacy；未知结果保持未知。新用量查询和单任务预算从同一 attempts 账本聚合，旧 turns 不成为第二套可写费用源。

## D32：月预算使用短事务准入与付费调用串行

共享 advisory lock 将累计费用/未知结果检查、待发意图和配置修改排好先后。月预算启用且已有付费请求在途时，其他任务等待容量而非要求人工批准；它们可取消。本地模型不受此付费容量约束。HTTP 请求不持有全局数据库锁。

已知费用到限、未知定价或本月有未核对费用时，创建持久化 monthly 请求。继续按钮只重新检查，不能绕过设置。按拥有者时区计算自然月；到期以 calendar 身份唤醒，重启后同样读取期限。费用按请求意图时间归档，与服务商发票周期分别理解。

代价是付费吞吐降低，单次在途调用可能超出剩余额度。当前没有可靠的输入/最终计费预估，不为硬上限创造虚假保证；仅在吞吐或准确预留有实证需求时讨论更复杂方案。

## D33：人工费用核对与原回执分离

未知费用允许拥有者按账单填写金额与依据。原 provider 状态、原单价和用量不覆盖，人工值单列，修改前后写 task_events。一般已知估算不被冒充为真实发票金额。接口只对拥有者开放并校验 Origin/金额。

证据：runtime-usage.json 覆盖时区/DST、双工作站容量、暂停与恢复、未知费用、真实本地兼容 SDK、期限重查、30 亿微美元、旧数据回填和实际手机/桌面用量页；53 条分页历史为显式样本。runtime-recovery.json 证明模型恢复语义保持。生产警示样式在不改主库设置的拦截响应中复查。

## D34：DBOS 定时唤醒，业务游标与运行先冻结

上游五种计划不全部等价于一条 cron，尤其任意 1—24 小时间隔、一次性、只补末次与修改计划。采用一个 30 秒 DBOS 调度器，串行扫描持久化计划；关闭框架心跳的自动补跑，由业务游标只受理末次并写跳过区间。启动立即触发，Web 不运行定时器。

运行、冻结输入及 next_run_at 同事务。随后调用原 submitTask。Task 成功而运行回执丢失时，用冻结来源键返回原任务。接受后修改/暂停/归档不删除运行；旧记录无 Task 回执的 running 显式失败。手动运行也有版本核对、持久请求键和复用语义。

每次使用独立 thread，仍按同一 Agent 工作站串行。代价是不同周期不自动共享聊天上下文；已有工作站文件、指定成果与后续验证记录负责跨周期比较。

## D35：日历时区、间隔锚点与自然周分别处理

PostgreSQL 在计划 IANA 时区内转换墙上时间；缺失时间向后顺延、重复时间使用变更后的一次。间隔小时使用已保存 next_run_at 的绝对时刻锚点。上一完整自然周以预定时刻计算，保存含首尾日期与 UTC 左闭右开边界，CSV 日期合同同步使用。

具体例子：纽约 2026-11-02 的上一自然周为 10 月 26 日至 11 月 1 日，跨 DST 回拨共 169 小时。恢复不会按当前日期重新解释。付费请求继续走已有月预算/取消/成果链路。

接受的代价：每 30 秒产生框架调度元数据，每次最多扫描/提交 50 条，历史页只显示最近 50 次并手动刷新。长期保留/容量放入 P7；新建计划请求级去重和完整合同编辑继续完善。条件通知仍待可信报表比较实现。
