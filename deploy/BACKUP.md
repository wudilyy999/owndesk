# 一致备份与干净恢复（F12，候选实现）

适用于本仓库的专用 Linux Compose 安装。操作端需要 Node.js 24、Docker CLI 与 Compose；直接运行 `node scripts/snapshot.mjs`，无需为该工具安装 npm 依赖。当前使用 format 2；早期 format 1 实验快照需在原环境重新制作完整快照。

## 1. 先明确恢复点

例如星期一 10:00 做了备份，10:30 Agent 发出过一笔外部请求，11:00 再恢复 10:00 的快照：外部网站仍可能保留 10:30 的效果。数据库回退无法撤销它。启动恢复服务前，需要核对备份之后的请求、服务商账单与外部记录，保留原站离线，避免两份安装同时工作。

首版采用短暂停机的一致快照，不承诺在线热备或任意时间点恢复。数据与主密钥分别保存；数据包本身也包含敏感的浏览器 Cookie、文件和数据库内容，应存入拥有者控制的加密介质。文件认证用于检查损坏/替换，不会加密数据包。

## 2. 停止写入

在仓库根目录执行：

```sh
docker compose --file deploy/compose.yaml --env-file deploy/.env \
  stop --timeout 60 caddy web worker
```

正常 worker 关闭会关闭本安装的工作站，让浏览器刷新 profile。PostgreSQL 保持运行供逻辑导出使用。工具会核对：

- Caddy、Web、worker 和同项目的一次性写入进程均已停止。
- 本安装所有 guest/viewer 均已停止。
- 数据库没有其他客户端连接。
- 每条工作站记录对应的 home 卷存在，镜像/迁移版本匹配。

存在在途模型调用或 Shell 时，停止过程可能产生未知结果；保留其记录，恢复后按原请求复核。遇到停止失败时先检查本安装的具体容器，勿停止其他项目或删除 home 卷来绕过检查。

## 3. 制作数据包与独立密钥文件

先准备两个拥有者专属目录，权限设为 700。以下路径只是示例；两个输出必须尚不存在，密钥文件位于数据包目录之外。

```sh
node scripts/snapshot.mjs backup deploy/.env \
  /srv/agent-data-backups/2026-10-25 \
  /srv/agent-key-backups/2026-10-25.env
```

成功后数据目录包含：

| 文件                    | 内容                                                                      |
| ----------------------- | ------------------------------------------------------------------------- |
| `database.dump`         | 完整 PostgreSQL 逻辑导出，包含业务、认证、Drizzle 和 DBOS                 |
| `artifacts.tar.gz`      | 宿主成果卷                                                                |
| `home-<agentId>.tar.gz` | 所有已存在的本安装 home 卷，包括浏览器 profile 和工作文件                 |
| `images.tar`            | 当时实际使用的 Web、worker、guest、PostgreSQL、Caddy 镜像；按镜像 ID 固定 |
| `manifest.json`         | 应用/依赖/迁移/平台清单、工作站和在途任务摘要、逐文件认证回执及清单认证   |

独立的 `.env` 副本保存原主密钥、安装标识、认证秘密与部署配置，不向终端输出。数据目录权限 700，文件及密钥副本 600。此副本不包含另行保存的初始拥有者密码；恢复后仍使用原登录密码。

签名清单在所有导出完成后写入。中途失败的目录保留用于诊断，缺少完整清单的目录不会被恢复器当成成功快照。工具拒绝覆盖已有备份，也不会自动恢复服务。

数据包不保存运行中的内存、guest 系统层修改或 X11 临时卷。恢复使用固定镜像和原 home/profile；需要常驻系统依赖时，应通过受控镜像版本管理。Caddy 的证书/CA 私钥不进入这个数据包，恢复时重新生成，拥有者需重新核对证书信任。

## 4. 离线核对

```sh
node scripts/snapshot.mjs verify \
  /srv/agent-key-backups/2026-10-25.env \
  /srv/agent-data-backups/2026-10-25
```

该命令不访问 Docker。它读取完整文件，核对原配置、认证清单和每个文件的长度/认证回执；缺失、损坏、替换、符号链接及清单中的越界文件名都会失败。它不执行数据库归档或模拟恢复，真正可恢复性继续由下一节验证。密钥或配置不匹配时，在恢复目标产生写入之前拒绝。

密钥文件需保持原样供核验。地址、端口和镜像固定值在恢复完成后写到新部署配置，再按实际环境核对；不要先修改原密钥副本来适配新主机。

## 5. 在干净主机恢复

先准备相同受验 OS/CPU 架构的专用 rootful Linux Docker 环境；跨 CPU 架构迁移尚未验证。把数据包与独立密钥安全送到操作端，保留原安装离线，使用本仓库匹配的 Compose/工具版本。

```sh
node scripts/snapshot.mjs restore \
  /srv/agent-key-backups/2026-10-25.env \
  /srv/agent-data-backups/2026-10-25 \
  deploy/restored.env
```

目标不得已经存在本安装的 Compose 容器、工作站或所需命名卷；新配置与恢复回执文件也不得已存在。恢复器不会清空已有安装来腾位置。

命令先完成所有本地认证检查，再导入包内的固定镜像、启动空 PostgreSQL、单事务恢复数据库、还原成果/home 卷，最后在一个事务内：

1. 删除旧网页会话与一次性桌面票据，要求重新登录。
2. 递增工作站 epoch、清除旧 bootId，让旧现场填写授权失效。
3. 暂停启用中的例程并推进计划版本，要求拥有者核对后重新启用。
4. 撤销 Telegram 配对代及旧按钮，要求重新配对；旧收发记录保留审计，不自动补发旧代通知。
5. 为历史任务保存恢复事件；保留任务、动作、模型请求及待复核决定，不把未知结果改成成功。

成功后**只有 PostgreSQL 运行**，应用尚未启动。新 `deploy/restored.env` 保留原身份/秘密并固定镜像 ID，旁边的 `.restore.json` 记录恢复点与在途任务。证书信任重新建立。若中途失败，保留具体失败与新目标数据供检查；先明确处理该次生成的部分目标，再选择新的干净恢复环境，勿盲目重复覆盖。

## 6. 核对与显式启用

1. 核对历史任务、成果字节、home 文件、记忆和凭据可用性；凭据使用专用安全流程，勿将明文打印到日志或发给模型。
2. 对照 `.restore.json` 和备份之后的外部记录，核对所有在途、未知计费和未知动作。恢复动作不构成再次发请求的授权。
3. 按部署说明重新建立/核对宿主网络策略。入口地址改变时核对 APP_URL、WSS、控制 IP 和证书；公共 DNS/HTTPS 仍保留独立放行条件。
4. 确认继续后才执行：

```sh
docker compose --file deploy/compose.yaml --env-file deploy/restored.env up -d --wait
```

重新登录，检查历史下载与待复核卡片。原未知调用按原流程等待拥有者决定。核对当地时间/漏跑规则后再启用例程，核对新配对身份后再启用 Telegram。

本工具覆盖本仓库的固定单库/单拥有者部署；自定义 PostgreSQL 全局角色、数据库外服务和跨版本数据导入不在这次恢复中。公开域名 ACME、普通公网网络、长期容量和整体 上游项目 对照继续分别验收。

## 7. 实验与证据

定向单元检查：

```sh
node --import tsx --test tests/snapshot.test.ts tests/action-receipts.test.ts
```

`tests/restore.ts prepare` 使用明确指定的隔离 Linux 实验主机和已有受控报表部署，实际制造一次外部提交中断及一次模型回答中断，然后制作快照。`restore` 在另一台空 Linux 引擎导入并验证；`validate` 用于在仅 PostgreSQL 运行、匹配恢复回执的条件下继续数据/运行验证，避免为测试观察错误重做整套导出和导入。

检查点文件包含实验账号、会话和模拟服务密钥，权限 600，勿公开。正式结论以工程 `docs/STATUS.md`、去秘密的 `docs/evidence/restore.json` 和对应原始记录为准；命令存在不代表完整恢复已通过。
